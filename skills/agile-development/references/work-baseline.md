# 工作基线与连续工作环境

这份参考把“开发迭代之外的工作”落成一套最小秩序：项目定位、战略目标、当前主线、
目标修正、工作日志、决策记录、提交边界、基础规范，以及谁维护、怎么维护。它不是
官僚文档；目标只有一个：让下一次任务能从稳定起点开始，而不是从零开始。

这份参考列的是通用检查项和缺省起点，不是固定流程。项目已有日志、决策、提交、评审、
维护或任务管理约定时，沿用它们，并在项目本地工作基线里指向这些载体；下面的格式、
节奏和角色只在项目没有现成约定时作为起点。不要为了满足这份参考新建一套并行的文档。

最小用法：先找权威位置，缺的记下来，不影响当前任务就先做；不要一次填完整套模板，
也不要把这些检查项当成开工门禁。

## 先认识项目，再定本地做法

这份参考列的是通用检查项，不是固定的文件布局。工作日志放哪里、决策怎么记、规范写进
哪个文件、分治和并行怎么落地，都要先看项目现状再决定。先做一次项目分析：

- 读 README、AGENTS.md/CLAUDE.md、CONTRIBUTING、docs/、issue tracker、CI 和脚本。
- 跑或核对安装、启动、测试、构建、lint；记录从干净检出到第一次运行的实际步骤。
- 看目录和模块边界、共享写入、生成物、分支和 worktree 惯例。
- 找现有载体：定位、目标、主线、日志、决策、规范分别已经放在哪里。
- 看 Agent 工具和协作方式：可用角色、并行隔离、评审和合并流程。
- 回看最近任务：哪些摩擦反复出现，哪些现有规范已经失效。

分析的目的不是写项目介绍，而是确定这个项目的基线放在哪里、由谁维护、哪些做法要适配
现有惯例。能从仓库读出来的，不重复问人；只问会改变方向的问题。

## 项目本地工作基线载体

把分析结论写进项目本地工作基线载体：优先复用已有 CONTRIBUTING.md、docs/ 或 AGENTS.md；
需要单独维护时再新建一个 md，并在 AGENTS.md/CLAUDE.md 里留一行指针。文件名和位置按
项目惯例（例如 `docs/agile-development.md` 或 `WORKING.md`）。一个项目最多新增一个
基线载体；缺失的记录先写进这个载体的短段落并指向已有来源。项目本来就有按类型分文件
的惯例时，沿用那些文件，不另建并行的基线文件。不要同时维护两份互相矛盾的工作基线。

如果写在 AGENTS.md/CLAUDE.md 的段落里，下文“这个文件”指该入口文件。它是索引和适配
层，不是第二份计划、日志或评估台账；具体内容仍放在各自的权威载体里。这个载体只记录
这个项目的具体做法和权威位置，不复制会过期的内容。建议内容：

| 项目问题 | 本项目做法（载体与规则） | 权威位置 |
| --- | --- | --- |
| 项目定位、战略目标 | 用哪一段/哪个文件承载；谁更新、何时更新 | README / `PROJECT.md` / docs |
| 当前主线 | 用哪个 issue/milestone/字段；owner 和复查日期以哪里为准 | issue tracker / milestone / `MAINLINE.md` |
| 任务与验收 | 任务来源、验收标准、状态更新用什么载体 | issue tracker / 任务表 / 短合同 |
| 工作日志 | 格式、位置、压缩节奏 | ... |
| 决策记录 | 格式/ID、状态、位置 | ... |
| 探索与草稿 | 实验、研究笔记、临时产物的位置和归宿 | ... |
| 提交/本地边界 | 分支、worktree、生成物、密钥的处理规则 | ... |
| 基础规范 | 提交、评审、测试、文档、完成定义的现有入口 | ... |
| 分治与并行 | 角色、ownership、接口裁决、通信、隔离、合并、团队规模判断 | ... |
| 环境改造 | 指标、停止条件、记录位置；before/after 数值放工作记录 | ... |
| 维护 | owner、复查节奏、需要跟踪的 1–2 个指标 | ... |

规则：

- 只写项目特定做法和权威位置；通用判断仍回到技能，不把技能正文抄进来。
- 优先指向已有权威来源，不复制会过期的内容；项目已有约定优先。
- 项目结构、工具链或主线变化时更新；定期删除过期条目。
- 小任务且已有基线时只更新必要条目；不要为了建文件而建文件。
- 新 Agent 只读 AGENTS.md/CLAUDE.md 和这个载体，应该能知道去哪里找权威信息。

## 一、项目定位

用一页写清：

- 项目是什么，为谁解决什么问题。
- 明确不做什么，避免范围漂移。
- 关键约束：时间、成本、技术、合规、团队。
- 成功标准：什么可观察结果算成功。
- 长期方向：未来 3–12 个月要去哪里。

放在项目已有的固定位置（例如 README、`PROJECT.md` 或 docs/），具体位置写进项目本地
工作基线载体。定位变化时更新，并在工作日志里记下原因。

## 二、战略目标与当前主线

- **战略目标**：3–12 个月的方向、当前阶段、非目标。不是任务清单。
- **当前主线**：同一时间只保留一条主线；写清验收、owner、依赖、复查日期。
- **其他工作**：明确标记为支撑、探索或搁置；不要让它们偷偷变成第二主线。
- **WIP 限制**：默认一条主线；超过就排队、降级或拒绝。支撑、探索或搁置工作也占容量，
  不能无限并行；紧急例外要记录原因和恢复点。

主线放在项目现有的权威载体（例如 issue tracker、milestone 或 `MAINLINE.md`），具体位置
写进项目本地工作基线载体；不要同时维护多份互相矛盾的版本。

## 三、目标修正

修正不是失败，拖着不修才是。触发信号：

- 新证据推翻主线的前提。
- 关键路径被阻塞，超过预算。
- 成本/收益发生明显变化。
- 外部需求或约束变化。
- 同一摩擦反复出现，说明目标或方法不对。

修正流程：

1. 记录旧目标、新目标、理由、证据、日期和影响。
2. 更新主线和相关工作日志。
3. 通知相关 Agent/人；把旧任务关闭、归档或转成探索。
4. 设下一次复查日期。

避免频繁摇摆：默认只在复查点修改目标；硬触发时随时记录并修正。每次修改都留下记录。

## 四、工作日志

项目已有工作日志时，沿用其位置和格式；以下是缺省模板。

按日期追加，每次会话或任务一段：

```md
## 2026-11-13 — <主线>

- 目标：
- 完成：
- 决策：
- 未决/风险：
- 下一步：
- 关联：commit / PR / 文档
```

任务中断时，额外写：

```md
- 状态：完成 / 中断 / 阻塞
- 恢复点：从哪里继续
- 现场：分支、worktree、临时文件、未提交改动
```

规则：

- 提交对后续有用的摘要；原始草稿、流水账留在本地。
- 每周压缩一次：合并重复条目，删除过期内容，保留决策和恢复点。
- 日志不是给别人看的表演，是给下一次会话的恢复材料。

## 五、决策记录

项目已有 ADR/决策记录时，沿用其格式和位置；以下是缺省结构。

追加式，不删除已接受的决策。每条包含：

- ID、日期、状态（提议 / 接受 / 取代 / 废弃）。
- 背景和问题。
- 考虑过的选项。
- 决定和理由。
- 后果和后续动作。

已接受的决策被新决策取代时，保留旧记录并链接到新记录。决策记录放在项目现有的
权威载体（例如 `docs/decisions/` 或 `DECISIONS.md`）；不要散落在聊天记录里。

## 六、提交与本地边界

项目已有提交、分支或评审规范时，以项目规范为准；以下是缺省原则。

**提交**（进版本库、共享、可复现）：

- 源代码、测试、文档。
- schema、迁移、非密钥配置。
- 决策记录、对后续有用的工作日志摘要。
- 可复现的脚本和任务模板。

**留在本地**（不进版本库）：

- 密钥、`.env`、凭据。
- 一次性实验、草稿、生成物、构建输出。
- 大数据、机器特定配置、个人笔记。

**实验**：

- 放本地分支或 worktree；不要和主线改动混在一起。
- 验证有价值后，rebase/squash 进主线；否则删除或归档。
- 先写 `.gitignore`，再开始实验；不要用 `git add .` 盲加。

原则：提交真相和理由，把脚手架和原料留在本地；永远不提交密钥。

## 七、基础规范

项目已有规范载体时，指向它；以下是缺省清单。

只写会反复用到的规则：

- 提交信息：动词开头，说明为什么，原子提交。
- 分支/主线：从主线拉分支，rebase 后快进；不产生无意义的 merge commit。
- 评审：什么改动需要独立 review；review 看目标和证据，不看自我解释。
- 测试：什么行为必须有可执行验收；测试期望来自规格。
- 文档：放在哪里，什么时候更新。
- 任务模板：目标、为什么现在做、验收、约束、决定权和验证方式；需要人决定的事项按
  [human-interface](human-interface.md) 给决策点。
- 完成定义：什么算 done；什么必须写明未验证面。
- 升级：什么情况必须问人。

规范放在 Agent 会读的地方（`AGENTS.md`、`CLAUDE.md`、`README`、`CONTRIBUTING.md`），
具体入口写进项目本地工作基线载体。规范是服务，不是 gate；每加一条，先问它防止哪种
重复摩擦。

## 八、谁维护，怎么维护

- **Owner**：项目负责人或主 Agent 拥有工作基线。
- **Steward**：多 Agent 或复杂项目可以设一个维护角色（人或子 Agent），负责日志、
  决策记录、清理、fresh context 测试和规范复查；不拥有战略决定权。单人项目不设
  Steward，由主 Agent 在交付时更新。
- **更新责任**：主 Agent/整合者在交付时更新项目本地工作基线；worker 只更新自己负责
  的记录；Owner/Steward 按选定节奏复查。
- **人**：保留项目定位、战略目标和重大取舍的最终决定权。

节奏按项目规模缩放：

- 每次会话：有值得下次恢复的内容时更新工作日志；没有就不写。提交前检查提交/本地边界。
- 每周：复查主线、目标、过期决策和临时文件；压缩日志。低频项目可以放到每个阶段。
- 每阶段：复查项目定位和战略；根据摩擦调整规范。
- 事故后：补决策记录，更新规范或环境，不只用口头解释。

指标（用来判断秩序是否有效，不是考核）：只选 1–2 个会改变决策的，不要求全上。

- 从 fresh context 恢复到可工作状态所需时间。
- 过期文档/决策数。
- 重复劳动和返工。
- 主线变更频率（是否频繁摇摆）。
- 提交卫生事件（密钥、生成物、大数据误提交）。
- 新 Agent onboarding 时间。

## 九、反模式

- 用文档代替判断；为秩序而秩序。
- 每个失败加一条规范或 gate。
- 不看项目现状，直接套用别的项目的文件布局、日志格式或团队规模。
- 项目本地基线载体变成第二份计划或日志，和权威载体互相矛盾。
- 为了建文件而建文件，小任务也走重流程。
- 同时开多条主线，WIP 爆炸。
- 工作日志变成流水账，没有决策和下一步。
- 提交一切，或什么都不提交；实验和主线混在一起。
- 目标频繁摇摆，没有修订记录。
- 维护者变成瓶颈；没有明确 owner。
- 把工作基线建设当成逃避开发的借口。

## 十、完成条件

建立或重整工作基线时：项目定位、战略目标、当前主线、任务与验收载体、工作日志、
决策记录、提交边界、基础规范、维护 owner 和节奏都存在且可用，项目本地工作基线载体
和必要的 AGENTS.md/CLAUDE.md 指针已经建立或更新；fresh context 的 Agent 能靠这些材料
恢复工作；目标和主线变更都有记录；临时实验有归宿。达到这些条件就回到开发迭代。

只是借基线推进日常任务时：本任务所需的定位、主线、任务/验收载体、记录位置、提交边界
和验证命令可用即可；缺项记录为未知或待办，不为了完成任务先补全整套基线，也不编造
owner、战略或复查日期。
