# 摩擦审计与改造点选择

这份参考把“环境很慢/很乱”变成一张可排序的投资清单。它不是完整的环境评估框架；目标
是找出最贵的重复摩擦，选一个最小改造点，然后用 before/after 证明它值得。评分和改造点
必须来自当前项目的真实任务；换一个项目，证据和优先级都要重新收集。

## 一、收集证据

从最近 3–5 个真实任务里记，不靠印象。先用最小四列筛：摩擦、频率、每次损失、改造成本；
只有进入候选的摩擦才填完整表。每条摩擦记录：

| 字段 | 内容 |
| --- | --- |
| 任务 | 哪个任务、什么日期 |
| 摩擦类型 | 入口、反馈、上下文、安全、协作 |
| 症状 | 具体卡在哪里，错误是什么 |
| 每次损失 | 分钟/小时/天，粗略数量级即可 |
| 频率 | 一周几次、每个任务几次 |
| 影响任务数 | 只影响这一个，还是影响同类任务 |
| 现有绕法 | 现在怎么绕过；绕法本身是否在制造新问题 |
| 根因 | 缺命令、缺数据、缺文档、缺隔离、缺观测等 |
| 候选改造点 | 最小可复用的改造 |
| 成功指标 | 改完后哪个数会变 |
| 停止条件 | 做到什么程度就停 |
| 回滚方式 | 失败怎么退回 |

## 二、排序

用 1–5 分估，不追求精确：

- 频率 `F`：1 一次，5 每个任务。
- 每次损失 `Loss`：1 几分钟，5 超过一天。
- 影响任务数 `A`：1 一个任务，5 所有同类任务。
- 改造成本 `C`：1 几小时，5 几周。
- 改造风险 `Risk`：1 可逆、局部，5 不可逆或影响共享环境。

优先级约等于：

```text
Priority = (F × Loss × A) / (C × Risk)
```

这里的 `Loss`/`Risk` 是环境改造排序用的，和工作图里的 `L`（关键路径）、`R`（风险
级别）不是同一组符号。

先做分数最高的；同分时选更可逆、更容易验证的那个。一次性的低分摩擦记录后跳过，不要
为它建平台。

## 三、before/after 指标

选两三个和摩擦直接相关的指标：

| 指标 | 怎么量 |
| --- | --- |
| 首次运行时间 | 从干净检出到主路径跑起来 |
| 首次验收时间 | 从任务开始到第一个可执行验收 |
| 相关测试周期 | 只跑相关测试的 p50/p95 |
| Flake rate | 重跑才通过的失败占比 |
| 手动步骤 | 完成一次主路径要执行的命令、点击、密钥配置 |
| 定位成本 | 新 Agent 找到入口和约定所需的 token/时间 |
| 整合返工 | 合并后修接口、冲突、环境差异的时间 |
| 逃逸缺陷 | 验收后才发现的环境类问题 |

用同一个任务或同类任务比较。没有改善就回滚或停止；不要用“平台建好了”当成果。

## 四、fresh context 测试

这是最接近 Agent 真实处境的验收：

1. 开一个没有历史对话的新 Agent。
2. 只给仓库、任务目标和时间/token 预算。
3. 观察它能否找到入口、安装、运行、测试，并到达第一个可运行或可验收点。
4. 记录它卡住的位置、猜错的命令、读错的文档、需要的提示。
5. 这些卡点就是下一个改造点；不要用你脑子里的隐性知识替它补全。

如果新 Agent 必须靠你口头解释才能跑起来，说明工作环境还没接通。

## 五、两个例子

### 测试慢且闪

- 症状：改一个小函数，跑相关测试要 8 分钟；偶发失败重跑才过。
- 损失：每个任务 2–3 次，每次 8 分钟；失败定位还要 10 分钟。
- 频率：每个任务；影响所有后端任务。
- 候选改造点：相关测试命令、测试数据 fixture、隔离外部依赖、并行分片。
- 成功指标：相关测试 p50 从 8 分钟降到 2 分钟；flake rate 降到可接受范围。
- 停止条件：主路径和常用边界能稳定重跑；不追求全量测试瞬间完成。
- 回滚：保留旧命令，新命令作为可选入口；fixture 改动可独立回退。

### 新 Agent 接不上仓库

- 症状：新 Agent 找不到入口，装错版本，跑错命令，读了过期文档。
- 损失：每次接手 1–2 小时；人类也要重复解释。
- 频率：每个新任务/新 Agent；影响所有任务。
- 候选改造点：README、AGENTS.md/CLAUDE.md 的入口地图、版本固定、一条命令启动、验证命令。
- 成功指标：fresh context 测试中，新 Agent 在预算内到达第一次运行。
- 停止条件：入口、命令、验证方式可直达；不写完整架构手册。
- 回滚：文档和脚本分开提交；旧命令保留一个版本。

## 六、校准

每次改造完成后记录：

- 实际收益是否达到预估。
- 改造花了多少时间，是否超出预算。
- 有没有引入新的摩擦或维护负担。
- 下一个最贵的摩擦是什么。

如果连续两次改造的收益低于成本，停止环境工程，回到主任务；这说明当前瓶颈不在环境，
或者改造点选错了。

## 七、失败模式

- 用“最佳实践”清单代替真实摩擦。
- 只记录症状，不记录频率和损失，最后按感觉排序。
- 把一次性的问题当成平台需求。
- 改造没有停止条件，越做越大。
- 只验证“命令能跑”，不验证新 Agent 能否独立到达验收点。
- 改造和功能改动混在一个分支，无法判断收益和回滚。
