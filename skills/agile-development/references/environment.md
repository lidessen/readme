# 开发环境与反馈循环

环境不是开发的背景，而是开发速度的一部分。Agent 每多等一次构建、多猜一次入口、多
修一次假失败，都会在后续任务里重复交税。环境改造的目标是形成有序、连续、可恢复的
工作环境：用真实任务找出重复摩擦，做最小、可验证、可回滚的改造。

环境改造不是平台瀑布。跨任务的重复摩擦改造，没有证据不立项；没有 before/after 证据，
不算完成。小摩擦直接修，不必先做完整审计；下面的排序和表格用于反复出现、值得投资的
摩擦。

当前任务被环境问题直接阻塞时，先做任务范围内的最小解阻，不必等重复摩擦证据；可复用、
跨任务的改造才进入下面的排序。

## 通用方法，项目本地做法

环境改造的方法通用，具体做法没有标准答案。同一个摩擦在不同项目里的频率、损失、改造
成本和可逆性不同；先认识项目，再决定改什么、用什么工具、改到什么程度。不要照搬其他
项目的改造清单。

项目分析至少看：入口和真实命令、测试/构建反馈、目录和所有权、已有文档和 Agent 入口、
并行与隔离方式、最近任务的重复摩擦。结论写进项目本地工作基线载体（见
[work-baseline](work-baseline.md)），包括本项目的改造点、验证命令、before/after 指标、
停止条件和回滚方式。没有经过项目分析，不从“最佳实践清单”直接立项。

## 先识别摩擦，不先建平台

从最近 3–5 个真实任务收集证据：哪里卡住、等了多久、重复了什么、哪些失败是环境造成
的。不要从“最佳实践清单”出发；从实际损失出发。新仓库没有历史任务时，把当前任务的
第一次安装、启动、测试和一次 fresh context 测试作为第一批样本，记录实际耗时和卡点；
积累到 2–3 个任务再排序。

| 摩擦 | 症状 | 证据 |
| --- | --- | --- |
| 入口 | 装不上、跑不起来、找不到入口、缺密钥或种子数据 | 新 Agent 从零到第一次运行的时间；手动步骤数 |
| 反馈 | 测试慢或闪、构建慢、错误信息无用、无法本地复现 | 相关测试周期；flake rate；失败定位时间 |
| 上下文 | 文档过期或分散、架构不清、约定隐含 | 新 Agent 找到可改文件所需的 token 和时间 |
| 安全 | 无回滚、共享状态、破坏性操作、权限不清 | 事故或接近事故；回滚时间；隔离缺口 |
| 协作 | 合并冲突、合同漂移、所有权不清 | 整合返工；冲突频率；接口变更次数 |

按“频率 × 每次损失 × 影响任务数 ÷（改造成本 × 风险）”排序，用数量级估即可。只处理会
重复发生的摩擦；一次性的环境问题记录后跳过，除非它正在阻塞当前任务。需要完整审计表、
评分和示例时，见 [friction-audit](friction-audit.md)。

## 选改造点：先修最贵的重复摩擦

改造点是能支撑多个任务的最小环境投资。候选优先满足以下条件，不必五项全满；不能
事前验证的，先约定成功指标、停止条件和回滚方式。

- 高频：最近多个任务都遇到。
- 高损失：每次浪费的时间、返工或风险大。
- 可复用：修一次，多个任务受益。
- 可逆：失败能回滚，不锁死技术选择。
- 可验证：能用 before/after 证明循环变快、变稳或更安全。

优先修关键路径上的瓶颈：它挡住的任务最多。不要先修“看起来先进”的工具。每个改造点
写清：解决哪种重复摩擦、成功指标、停止条件、回滚方式。没有停止条件，就会变成平台
工程。

常见改造点（按项目实际情况选择，不是清单）：

- 一条命令从零到可运行：安装、启动、测试、种子数据、重置。
- 相关测试的快速命令和稳定 fixture；失败能本地复现。
- Agent 入口地图：README、AGENTS.md/CLAUDE.md、模块图、任务模板、验证命令。
- Agent 工作环境：技能、记忆、任务入口、模型和权限配置、成本日志；让 Agent 不必每次
  重新摸索。
- 隔离工作区：worktree、分支、预览环境、沙箱；并行 Agent 不共享写入。
- 主路径可观察：日志、trace、截图、请求响应、测试报告。
- 本地与 CI 一致：版本固定、命令一致、干净检出可复现。
- 安全边界：密钥、权限、迁移、备份、回滚。

任务特定的安全（这次迁移的备份、回滚演练、恢复验证）属于任务验收，不参与重复摩擦
排序；只有多个任务都需要的安全能力才作为环境改造。

## 改造：最小闭环，先通后优

先做能跑通的最小版本，不先做通用平台。优先用现有工具和项目惯例；不要为了环境改造
引入新框架，除非它明显缩短关键路径。

把环境改造当成产品改动：有验收、有测试、有文档、有回滚；尽量和功能改动分开提交，
混在一起时要能单独回滚。改造本身也可以用主技能的起胚、合形和打磨循环；范围大时按
独立切片分治。

常见顺序：

1. 让主路径一条命令跑起来。
2. 让相关测试快速、稳定、可重复。
3. 让新 Agent 能靠仓库文档找到入口和验证方式。
4. 让并行工作有隔离和合同。
5. 再补观测、性能、CI 一致性和更完整的工具链。

不要在第一步就做全套 CI/CD、全量监控、通用脚手架；这些是后续改造点，不是入场费。

## 验证：用真实任务和 fresh context 验收

按改造目标选 2–3 个能判断摩擦是否改善的指标，记录改造前后；例如：

- 从干净检出到第一次运行的时间。
- 从任务开始到第一个可执行验收的时间。
- 相关测试周期（p50/p95）和 flake rate。
- 完成一次主路径所需的手动步骤。
- 新 Agent 定位入口和约定所需的 token 和时间。
- 整合返工和逃逸缺陷。

不是每次都要全测；选与这次摩擦最相关的。涉及入口、上下文恢复或新 Agent onboarding
的改造，做一次 fresh context 测试；其他改造按需。

Fresh context 测试：开一个没有历史上下文的新 Agent，只给仓库和任务，看它能否在预算
内到达第一个可运行或可验收点。它卡住的地方就是下一个改造点。

用同一个任务或同类任务做 before/after；没有改善就回滚或停止。不要用“我们建了平台”
当成果。

## 固化与收束

把命令写进项目本地工作基线载体或它指向的权威位置（README、AGENTS.md/CLAUDE.md、脚本
或 docs/），并确保它们真的能跑；不要让文档和脚本分叉。命令要能从干净检出执行，版本要
固定。

只加能防止具体失败的检查。每道 gate 说明拦什么失败、为什么在这里拦、删掉后谁接回
保证；能降级为反馈的不阻断。不要为每个历史失败加一道门。

删除临时脚本、重复命令、一次性脚手架；保留可复用的最小集。记录剩余摩擦和下一步，
不把“环境还不完美”当成阻塞；回到主任务。

## 反模式

- 平台优先的瀑布：先建通用平台，几个月不做真实任务。
- 照搬别的项目的改造清单，不从本项目的真实摩擦出发。
- 为每个失败加 gate 或检查，环境越来越重。
- 为假想需求过度抽象；用一个新框架解决一个脚本能解决的问题。
- 改造没有 before/after 指标，做完不知道有没有用。
- 环境改造和功能改动混在一起，无法回滚。
- 追求“完美环境”而 gold-plate；忘记环境改造的目的是支持主任务。
- 只有作者能用的工作环境：没有文档、没有复现、没有权限说明。
- 把“环境改造”当成逃避困难任务的借口。

## 完成条件

重复摩擦有 before/after 证据地减少或消除；改造点、验证命令和指标已经写进项目本地
工作基线载体；新 Agent 能靠仓库文档到达第一个可运行或可验收点；关键命令可复现，文档
与脚本一致；改造可回滚，临时脚手架已清理；主任务已经可以继续。达到这些条件就回到
主任务，不为了环境而环境。
