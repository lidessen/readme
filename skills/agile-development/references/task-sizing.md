# 任务规模与团队规模量表

这份参考把 `SKILL.md` 里的工作图指标变成一张可填写的量表。它是代理指标，不是行业标准；
只在任务超过单 Agent 快车道时使用，小任务不要为填表付出成本。先算 `N`、`W`、`T`；
超过快车道再算其余量。下面的表是算例，不是查表；同样的形态可以合并、串行或换一种
切法，不同项目也会得到不同的团队规模。估不清就先用最小团队试，做完再校准。

## 工作图

节点是一条可独立验收的垂直切片。每个节点记录：

- 验收证据：什么可观察结果算完成。
- 上下文估算 `T_i`：读改文件、文档、测试和预期工具输出的 token。
- 涉及模块/文件。
- 阻塞依赖：合同、数据、共享文件、待定决策。
- 共享写入：会被多个节点写的文件、服务、表或配置。

边是阻塞依赖。共享写入资源单独列出；它们不能被两个写者同时改。

## 指标

| 指标 | 定义 | 怎么量 |
| --- | --- | --- |
| `N` | 节点数 | 数工作图节点 |
| `W` | 最大 ready 宽度 | 拓扑分层，取同一层可开工节点数的最大值 |
| `L` | 关键路径 | 最长依赖链的节点数 |
| `E` | 跨节点合同边 | 数跨节点边中需要接口或合同变更的 |
| `X` | 共享写入资源 | 数被两个以上节点写的文件、服务、表或配置 |
| `T` | 上下文总量 | 节点 `T_i` 去重后加总；英文约 4 字符/token，中文约 1–2 字符/token，有 tokenizer 就直接量；再留 30–50% 余量 |
| `R` | 风险级别 | `R0` 局部可逆；`R1` 跨模块或公开合同但可逆；`R2` 权限、支付、迁移、安全、外部合同或高影响面 |
| `U` | 未知簇 | 数必须靠探索才能回答的问题；每个问题默认 15–30 分钟或一次探索调用，live/外部批次按一个批次周期计 |
| `I` | 整合容量 | 主 Agent 在一次整合窗口里能合并并验收的分支数；从最近三次任务的 review 和测试时间估，新项目先取 2 |

`T` 的有效上下文阈值通常取模型窗口的 50–70%。超过就必须拆，即使 `N=1`；按上下文边界
拆，不按文件数拆。`T` 的估算误差通常很大，记录估算和实际，校准下一版。

`I` 的起点可以取 2–3，新项目先按 2 估。它比 worker 数量更容易成为瓶颈：如果合并队列
在增长，加 worker 只会让队列更长。

## 快速分诊

先看两个比值，不要先看总工作量：

- `T / T_eff`：上下文压力。大于 1 必须拆上下文，即使只有一个交付节点。
- `W / I`：并行压力。大于 1 说明可并行的工作超过整合容量，先加整合、缩域或串行。

再看三个放大器：`E + X` 高说明接口和共享写入重，先设契约裁决或整合；`R1/R2` 加独立
验收；`U>0` 加时间盒探索。五个信号都没有时，通常可以走单 Agent 快车道；有信号也不
一定组队，先看它是否真的拖慢当前任务。

## 项目本地化

工作图指标是通用的，具体分工不是。角色怎么命名、怎么通信、是否设三人组、如何合并，
取决于项目的 Agent 工具、代码边界和现有协作惯例；同一张工作图在不同项目里可能得到
不同的团队规模和不同的组织形式。不要照搬示例里的“5 个 Agent”或“三人组”。

先按项目实际画出工作图，再决定职责域和人数；把本项目采用的规则写进项目本地工作基线
载体，下次任务复用并校准。

## 团队规模算例

下表是算例，不是查表；先按工作图算出职责域和并行压力，再用 `I`、协调跨度和项目工具
修正。

| 工作图形态 | 团队规模 | 说明 |
| --- | --- | --- |
| `N=1`、`T` 装得下、`R0`、`U=0` | 1 个 Agent | 单 Agent 快车道 |
| `N>=2`、`W=1`、`T` 装得下、`R0`、`U=0` | 1 个 Agent | 串行执行；节点多不等于要加人 |
| `W=1`、`R1/R2`、`U=0` | 2 个 Agent | owner + 独立验收者 |
| `W=1`、`R0`、`U=1` | 2 个 Agent | owner + 探索者 |
| `W=1`、`R1/R2`、`U=1` | 3 个 Agent | owner + 验收者 + 探索者 |
| `W=2`、`R0`、`U=0` | 2–3 个 Agent | 主 Agent 兼任一个 worker 时 2 个；不兼任时 3 个 |
| `W=2`、`R1/R2`、`U=0` | 3–4 个 Agent | 两个 worker + 验收者；主 Agent 兼任时 3 个 |
| `W>=3`、`R0`、`U=0` | `min(W, I, 5)` 个 worker + 主 Agent | 主 Agent 兼任一个 worker 时减 1；`I<2` 时先加整合或缩域，不硬上 |
| `W>=3`、`R1/R2`、`U=0` | 上一条 + 1 个独立验收者 | 主 Agent 兼任 worker 时减 1；`U>0` 另加探索者或由现有角色兼任 |
| `T` 超过有效上下文 | 至少拆成 2 个上下文域 | 不管 `W` 是多少 |

通用规则：

- 主 Agent 跨度约 3–5 条活跃线；超过先分层或串行。
- `E` 或 `X` 高：先设契约裁决或整合角色，再放 worker。
- `L` 长而 `W` 小：并行收益有限，先缩关键路径或派探索者。
- `R2` 的验收者有否决权；实现者不能自判通过。
- `R1` 的独立验收证据可以由 fresh review、独立测试设计或另一个 Agent 提供，不一定
  单独占一个编制；`R2` 需要独立验收者。
- `U>0` 的探索者可以独立设置，也可以由主 Agent 或现有角色兼任；纯 spike 可以只有
  一个 Agent。
- 节点大小差异大时先拆大节点；同一个节点只有一个写者。
- 新增一线前算账：关键路径缩短 > 启动 + 上下文 + 接口 + 整合 + 返工。

## 两个例子

以下数值仅示意，用来展示判断顺序，不是标准答案；实际按项目测量。

### 小 bug：空指针

- 节点：1 个（修 handler + 回归测试）。
- `N=1`、`W=1`、`L=1`、`E=0`、`X=0`。
- `T`：约 20k token，装得下。
- 先做风险检查：如果 handler 触及支付、认证、权限或租户数据，就是 `R2`；即使一行，
  也要独立验收，不走快车道，团队为 2 个 Agent。
- 否则 `R0`、`U=0`，团队为 1 个 Agent。

### 跨模块功能：OAuth 登录

- 节点：4 个（合同/会话表、API 换 token、Web 回调、移动端深链）。
- `W=3`（合同完成后 API、Web、移动端可并行）；`L=2`。
- `E=3`（合同接口）；`X=1`（会话表）：由合同节点唯一写入，其他节点通过合同读写；
  如果两个并行节点都要写，先隔离或串行。
- `T`：三个代码库加起来超过单 Agent 有效上下文。
- `R2`（认证和安全），`U=1`（第三方 provider 的怪癖）；探索结果先于合同冻结，合同
  owner 必须消费它。
- `I`：约 2（示例取保守值；实际可能 2–3）。
- 团队规模：主 Agent + 2 个 worker（`min(3, 2, 5)=2`）+ 1 个验收者 + 1 个探索者 =
  5 个 Agent；如果主 Agent 兼任一个 worker，则 4 个。合同裁决由主 Agent 兼任；如果
  独立设置，团队规模加 1。先设合同裁决，再放 worker。

## 校准

使用了工作图或多 Agent 的任务，结束后记录：

- 估算 `W/L/T` 与实际。
- 实际并行收益：关键路径缩短了多少。
- 整合返工：合并后修接口和冲突花了多少。
- 逃逸缺陷：验收后才发现的问题。
- 验收时间：从开工到用户可见结果。

单 Agent 小任务只记实际耗时和返工，不填量表。用这些数据调整阈值。没有测量，就不要用
“任务大”或“三人组”当团队规模理由。把稳定下来的规则写进项目本地工作基线载体，下次
任务复用。

## 失败模式

- 用文件数代替 `T`。
- 把共享写入的节点算成可并行。
- 忽略 `I`，用加 worker 解决整合瓶颈。
- 把 3 当目标，而不是工作图的结果。
- 把示例里的团队规模当标准，不看项目工具和边界。
- 填表比任务本身还费时间；小任务直接走快车道。
