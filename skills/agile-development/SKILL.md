# Agile Development · 先建基线，再起胚打磨

开发不是从第一行代码开始，也不是把设计、实现、测试三层各自做完再拼起来。它从可
持续的工作基线开始，再对同一个整体做多轮塑形：先把大形立住，再逐轮增加分辨率。
第一轮就该有能运行、能看到主路径的整体；分治和并行用来缩短到达第一个整体的时间；
冗余用来探索和验证，但最终只保留一个权威实现。

瀑布式做法把设计、实现、测试当成三个依次签收的阶段；这里把它们当成同一个循环里的
三种活动，按需要反复进入。敏捷不是少做，而是短周期交付可验收的增量。粗糙只允许出现
在整体尚未成形的地方；行为、契约和验收不能含糊。

阶段不是一次性签收；工作基线、起胚、合形、打磨之间可以反复，发现形状不对就回到
定形或基线。

下面的顺序和检查项是默认启发式，不是开工门禁。能直接做的小任务直接做；某个步骤如果
没有缩短反馈、降低风险或提高验收质量，就跳过。安全责任（`R2`、硬边界、行为保持验收）
例外，不能以敏捷为名跳过。

最短路径：读任务 → 找到现有验收方式 → 起胚跑通主路径 → 按需打磨 → 验收。只有遇到
基线缺失、环境阻塞、分治判断或高风险时，才展开后面的小节。

先判断任务形态：先看有没有现成的工作基线；没有也不阻塞，按需要补。被环境直接阻塞时
先看“环境解阻”，即使任务很小；否则小任务可走“快车道”；其余按定形 → 起胚 → 合形 →
打磨推进。需要完整基线、团队规模或环境方法时，再读对应 reference。

## 先认识项目，再定本地做法

这套方法是通用的；它给的是判断顺序和检查项，不是固定的文件名、命令、角色表或团队
规模。工作图决定需要哪些职责域和多少并行；项目现状、已有载体和 Agent 工具决定这些
职责怎么落到具体 Agent 上。先认识项目，再决定本地做法；不要把示例当成通用标准。

项目已有更短的开发循环、验收命令和记录方式时，直接沿用；本技能只补缺的判断和验收，
不要求改流程、改叫法或新建载体。

首次进入项目时，先做与任务相称的快速认识；只有建立或重整基线、接手陌生仓库，或任务
确实需要时，才做完整分析。已有基线且不改变结构时，只核对与任务相关的一两项。完整
分析至少看：README、AGENTS.md/CLAUDE.md、CONTRIBUTING、docs/、issue tracker、CI 和
脚本；从干净检出能否完成安装、启动、测试和构建；模块边界、共享写入和分支惯例；现有
定位、主线、日志、决策和规范分别放在哪里；最近任务里反复出现的摩擦。能从仓库读出来
的，不重复问人。

只有这个项目会持续使用这套方法时，才把结论落到项目本地工作基线载体：单独一个 md，
或 AGENTS.md/CLAUDE.md 中的对应段落；单独成文时在 AGENTS.md/CLAUDE.md 里留一行指针。
一次性任务不必生成文件，把结论留在交付说明里即可。优先复用已有载体；没有合适载体时
再新建，一个项目最多新增一个基线载体。载体只写项目特定决定和权威位置，不复制通用
方法；通用方法变化时只改技能，不要求每个项目跟着抄一遍。项目已有 plan、workflow、
验收日志时，载体只指向它们，不复制内容。小任务且基线已清楚时，直接开工，不要为了
生成文件而生成文件。用户只要求评估或没有写权限时，把基线作为建议输出，不强行落盘。

## 按当前主导约束定兼容与测试姿态

兼容、迁移和测试的投入不是固定配方，也不跟随项目年龄或“早期/成长/维护”的阶段
标签，而是跟随当前的主导约束：这一次改动或这个子系统此刻真正限制策略的东西。
从证据识别，不从印象套用：

- 谁在实际消费：外部消费者、真实用户、下游仓库，还是只有本仓库的开发者。
- 已成立的承诺：公开契约、已接受的 API 与数据格式、监管与合规要求、安全义务、
  本次任务的实际授权。
- 风险与反馈需要：失败的影响面、反馈要多快、数据与安全是否不可逆、改动面大小。

同一项目里各子系统的成熟度可以不同：受真实消费者约束的模块，与同一仓库里尚无
消费者的实验模块，主导约束不一样。逐个子系统、逐次改动判断，不把整仓的阶段
标签套到每一处。

由此推导兼容与测试姿态。下面的对应是启发示例，不是阶段规定，也不是已验证的
收益规律：

- 主导约束是找到正确形状、尚无外部消费者和兼容承诺时：直接修改目标设计并验收
  新形态；不为想象中的未来消费者预建过渡兼容层、双写或迁移脚手架。这不等于
  不测试——主路径和必要边界照常要有可执行的验收，只是回归面随真实使用者收缩。
- 已有真实用户与合同时：兼容成为设计输入；做有度量的迁移（版本化、弃用窗口、
  迁移说明），验证受影响消费者，并按约定安排迁移成本。
- 主导约束是维护既有消费者时：保护已成立的契约、数据与安全，同时按轮次偿还
  旧债；成熟不是永久保留全部 legacy，而是让每次删除带着消费者与回归证据。

已有义务高于阶段叙事：真实消费者、用户数据、监管、安全、已接受的合同和授权，
项目多早都要尊重；反过来，项目多成熟也不能拿“历来如此”拒绝还债。抽象阶段
不能替代目标、安全和具体风险判断，也不要求每个任务先跑一遍成熟度评估；小任务
照走快车道，姿态在定形时顺带确定。

约束会变，策略随之重议。触发重议的例子：出现第一个外部消费者、接受公开合同、
监管或安全事故、使用量或失败代价明显变化、旧债开始拖慢当前任务。重议后写明
执行效果：这次保留什么、迁移什么、删除什么、验证什么，优先级从哪里移到哪里；
按需记录在已有任务或工作基线中，不另建评估台账。

测试观察层与保障的具体比较，用同一份约束作输入，按
[risk-driven-testing](https://github.com/lidessen/skills/blob/main/skills/risk-driven-testing/SKILL.md)
选择；跨部分的过渡与整体演进设计交给
[architecture](https://github.com/lidessen/skills/blob/main/skills/architecture/SKILL.md)。

## 工作基线：最小秩序

没有工作基线，每个任务都从零开始：上下文、决策、状态和规范不积累，Agent 会漂移，
日志和提交各写各的，主线不清，目标过期也没人修正。工作基线不是官僚体系，而是让后续
迭代能从稳定起点开始的最小秩序。

开始任务时，先看与这次任务相关的信息有没有权威位置：任务与验收写在哪，当前主线是
什么，工作日志和决策记录在哪，提交/本地边界，基础规范。有就直接用；缺的记下来，按
影响补，不影响当前任务就先做，不要为了补齐基线停下开发。项目定位、战略目标和当前主线
至少读到与本次任务相关的部分；维护节奏在需要时再查。优先复用 README、
AGENTS.md/CLAUDE.md、CONTRIBUTING、issue tracker 和 docs/，不要另建一套重复文档。

任务小且基线清楚时直接开工，不必逐项检查；基线缺失且影响这次任务时，补最小的一项
即可。建立或重整完整基线时，读 [work-baseline](references/work-baseline.md)；它给模板、
维护节奏和指标，不要求每个任务都填完整套。

## 带目标工作，不只执行步骤

任务不是一串待办，而是一个目标在项目里的位置。开工前要知道：要达成什么、为什么现在
做、它服务哪个项目目标或主线、什么算更好。任务描述可能只是达到目标的一种手段；先理解
背后的用户问题和约束，再判断这条路是否值得走。只知道步骤不知道目标，遇到取舍就会
漂移：该简化时加机制，该停时继续抛光，或者做出方向相反但局部正确的实现。

团队共享这套方法和项目的目标上下文：定位、战略目标、当前主线、关键决策和验收标准；
知道为什么这样推进，遇到新情况能按原则判断，而不是等指令。给子 Agent 交代目标和边界，
不只给步骤。理解目标后，可以在授权范围内选技术默认、简化实现、修掉挡路的摩擦、提出
更简单的路径或更好的验收；这不是自由扩范围。改目标、改公开合同、动权限/支付/迁移等
硬边界、做不可逆操作，仍由人类或明确授权的 owner 决定。发现任务与目标冲突，带证据
提出，不沉默执行，也不擅自改方向。

“超预期”是用更少的机制达到目标、把一次性工作变成可复用能力、提前暴露风险，让项目比
任务开始时更好，不是范围外抛光。改进仍要过验收，并在交付说明里说清改变了什么、为什么
值得。

## 和人交流：少量、自足的决策点

人类是当前不可缺的决策者，但人不会通读完整上下文。交流的目标不是把信息倒出去，而是
让人在有限注意力下做出好决定。默认每次只给 2–3 个决策点；每个决策点自带必要上下文：
要定什么、为什么现在定、选项和各自后果、建议、不定的后果、是否可逆。需要认真读的
部分控制在约 500 字以内（起始预算，按实验调整）；背景、证据和细节放到链接、附录或
文档里，人需要时能展开。任务内的本地提交、分支和可逆检查点默认由执行者完成，不作为
人的决策点；推送、公开、发布和不可逆操作才升级。

每个决策点独立成立，不让人回答“上面第 3 项”。选项用完整说法，不只给 A/B 或编号；
每个选项自带做什么和后果，没看过前文的人也能选。没有决策时不要强行要人确认：状态汇报
只给结论和链接，需要决策时明确说“需要你定什么”。超过 3 个决策点时，先用授权和默认值
解决能解决的，剩下的分批或升级，不要打包成长文。`R2` 否决、不可逆授权、目标冲突和
范围变化必须走这个接口。完整模板、反模式和实验方法见
[human-interface](references/human-interface.md)。

## 先走快车道

单节点或可串行执行、上下文装得下、低风险（`R0`）、无未知（`U=0`）、不触碰硬边界的任务，
可以压缩成一轮：看一眼现有基线，有就用；没有就直接定形、起胚打通主路径，做一次必要
打磨，验收。`R1`/`R2`（跨模块或公开合同，以及权限、支付、迁移等高风险）或触及硬边界
的任务不走快车道。

质量地板不变：至少一个可执行的验收检查；已有工作日志、提交边界和项目本地基线时更新
必要条目，没有时在交付说明里写一句为什么不需要；明确说出未验证面，不把“只跑了 lint”
说成行为已验证。速度来自小批量、短反馈和只跑相关检查，不来自跳过测试设计或验收。

### 取证批次：交付物是证据

如果任务只是重跑回归、验收、基准或复现批次，交付物是证据而不是行为改动，走取证快车道：
固定引擎、提交、产物哈希和夹具来源；先跑一次完整冒烟穿过真实入口；冒烟不过先修引擎，
不进入正式批次；正式批次串行并记录分母；不拼接不同引擎或构建的数字；收尾只留批次 ID、
数字和失败归因。先采用项目或批次约定的通过线和硬规则；首见率、耗时这类诊断数字单独
记录，不临时升级为通过线。不要把取证任务套成塑形、起胚、合形流程。

## 环境解阻：先修反馈循环

当前任务被环境直接阻塞（装不上、跑不起来、缺种子数据、测试无法复现）时，先做任务
范围内的最小解阻，不必等重复摩擦证据；可复用、跨任务的改造才进入投资排序。

同一个环境摩擦重复出现、正在拖慢当前任务时，先做最小改造，不要在每个任务里绕；跨
任务的更大改造再进入投资排序。排序时按“频率 × 每次损失 × 影响任务数 ÷（改造成本 ×
风险）”，选一个最小、可逆、可验证的改造点；小摩擦直接修，不必算分。先做最小闭环，
用 before/after 和 fresh context 验收；没有改善就回滚或停止。环境改造是支撑层，不是
平台瀑布。任务特定的安全（备份、回滚演练、恢复验证）属于任务验收，不参与重复摩擦
排序。

完整方法见 [environment](references/environment.md)，审计表和评分见
[friction-audit](references/friction-audit.md)。

## 先定形，不先定完

明确用户要的结果、验收依据、现有代码位置和项目已有检查。先确定这次任务的“整体”：
哪条端到端路径必须成立，从哪里进入，在哪里观察，什么条件下算完成。再把它切成足以
开工的独立切片；需要判断分治时，画出切片、依赖、共享写入和验收组成的最小工作图。

不需要一次拆到底，也不需要先写完整设计文档。验收标准和范围放在团队会看的地方：
现有 issue、ticket、任务表，或交付说明里的一段短合同；不另建第二份计划。

先找最可能推翻当前假设的未知，把它排到前面。能在几分钟内用真实代码回答的问题，不写进
计划；必须靠实现才能回答的问题，用最小起胚去回答。纯探索任务（spike）的交付物是决策，
不是可运行行为：写清问题、时间盒、证据、可行/不可行/未知、选项和放弃条件。允许
在本地分支/worktree 用隔离探针并丢弃，不必走真实入口；负结果也是完成。核心设计选择用
[design-forge](https://github.com/lidessen/skills/blob/main/skills/design-forge/SKILL.md)
或 [architecture](https://github.com/lidessen/skills/blob/main/skills/architecture/SKILL.md)
处理，实证可行性用 spike。

定形只做到能开工。技术默认、现有惯例和可逆选择直接作出，并在交付时写明假设；只有会
改变产物、公开契约、权限或不可逆授权的缺口才停下来问，并按“和人交流”整理成决策点，
不把整份分析推给人。

## 第一轮：快速起胚

第一轮只做一件事：让任务以最薄的方式从头到尾存在。起胚要穿过与风险相称的真实入口，
不是另做一个独立 demo；`R0` 的单元或合同级复现即可；UI、集成、`R1` 和 `R2` 要走真实
入口。内部可以丑：允许 stub、假数据、临时重复、硬编码配置和手工步骤，但必须标出来，
并记入待清理清单（位置、替换轮次、验收检查）。

硬边界不能假或绕过：密钥、权限、支付、迁移、事务、外部合同和不可逆副作用；需要外部
依赖时用项目已有的 sandbox/test 凭据，不要把真实密钥或鉴权绕过写进代码。

起胚阶段不做长期抽象，不抛光内部，不写完整测试，不补文档。它不是为了交付，而是为了
把整体形状和接缝暴露出来。起胚跑不通，通常说明定形错了，不是实现不够努力；纯探索任务
例外，跑不通可以作为“不可行”的证据。起胚至少留一个能重跑的观察：冒烟测试、CLI 调用、
请求响应、截图或端到端脚本。“代码写完了”不是观察。

## 分治与并行：先划职责域，再决定谁做

先划职责域：切片 owner、验收/反证、未知探索、契约裁决、整合、临时支援。一个域至少
要说清决定权、产物和验收方式；接口或边界还说不清时，先合并、先探索或先起胚，不要
把不清楚的域硬分出去。

Agent 主导的开发默认是一个主 Agent 加一个工作小组，而不是一个 Agent 包打天下。主
Agent 保留整体形状、公共接口、合同和最终验收；工作小组按工作图推进。单 Agent 只用于
工作图只有一个节点且 `R0`、`U=0`、上下文装得下，或节点虽多但 `W=1`、`T` 装得下、
`R0`、`U=0` 的串行任务。项目只有单 Agent 能力、预算或工具限制时，按串行、分上下文
或分阶段执行，不为了形式强行组队；明确哪些验收可以自验、哪些必须等独立验收或人工
确认。

需要判断是否分治、或任务超过单 Agent 快车道时，先画最小工作图，并先算 `N`、`W`、`T`；
超过快车道再算 `L`、`E`、`X`、`I`、`R`、`U`。指标定义、分诊和团队规模算例见
[task-sizing](references/task-sizing.md)；它按需使用，不是新门禁。

先看分诊：`T` 超过单 Agent 有效上下文，或 `W/I` 大于 1 时，不能直接走单 Agent 快车道；
先加整合、缩域、串行或拆上下文，再决定团队规模。团队规模按这些规则决定，不按行数、
文件数或“感觉很大”：

- 单 Agent：`N=1` 或 `W=1` 可串行、`T` 装得下、`R0`、`U=0`。
- 并行：`W>=2` 才考虑；worker 数约为 `min(W, I, 5)`。`I<2` 时瓶颈在整合，先加整合或
  缩域，不要硬上两个 worker。主 Agent 可以兼任一个 worker。
- `R1`/`R2`：不能由实现者自判。`R1` 至少要有独立验收证据（独立测试设计、fresh review
  或另一个 Agent）；`R2` 加独立验收者，其否决不能被主 Agent 覆盖，只能升级给人类
  owner。`R1` 的分歧由主 Agent 基于证据裁决并记录。
- `U>0`：按未知簇加探索者，每个带时间盒；探索者可以由主 Agent 或现有角色兼任；纯
  spike 可以只有一个 Agent。
- 主 Agent 的协调跨度约 3–5 条活跃线；新增一线前算账：关键路径缩短 > 启动 + 上下文 +
  接口 + 整合 + 返工；算不过就串行或合并域。

这些数字是估算起点，不是开工门槛；估不清就先用最小团队试，做完再校准。

可以本地化的是组织形式：角色命名、通信、由谁兼任、具体人数；不可本地化的是安全责任：
`R1`/`R2` 的独立验收、`R2` 的否决、硬边界、行为保持验收。项目惯例不能取消这些责任。独立验收和 fresh
review 可以是同一个角色；只有证据类型不同（例如行为验收 + 安全审查）时才加第二个，
并说明新增覆盖。

共享文件、共享服务或同一份状态只允许一个写者；需要并行时先隔离副本或明确归属，再
整合。没有 sub-agent 或隔离工具时，按同一工作图顺序串行，主 Agent 依次承担各职责域；
并行只在有真实隔离和独立上下文时使用。如果瓶颈是共享的 live 机器、浏览器 profile、
外部服务或单套凭据，先串行或隔离；worker 数不能解决这类瓶颈。

冗余是投资，不是默认浪费。允许为了缩短关键路径而重复探索、并行做候选；只有在证据
类型不同或能明显缩短关键路径时，才让多个 reviewer 独立检查。判断标准是它是否缩短了
关键路径，而不是它是否绝对必要。不允许留下多份权威实现、重复测试、没有选择点的 Agent
团队或永久脚手架。每一份冗余都要有选择点和清理点：用演示、测试、基准或接口匹配度选出
胜者，其余在交付前删除或合并。候选数量保持小，通常 2–3 个；超过这个数，先问是不是
定形没做好。

需要组织 sub-agent、消息、等待和接合时，按
[divide-and-conquer](https://github.com/lidessen/skills/blob/main/skills/divide-and-conquer/SKILL.md)
的机制执行；本技能决定为什么分、何时分、分到什么程度。

## 合形：先让整体成立

按依赖顺序合并切片，先解决接口和接缝，再补局部细节。合并后跑一遍完整路径，确认整体
仍然成立。局部切片都通过，不代表接合正确；主 Agent 要在合并后的版本上检查调用链、
共享状态和真实入口。

某条工作线卡住整体时，先 stub 它并继续推进其余部分，不要让一个局部把整体拖住；等
整体稳定后再回来替换。但硬边界（`R2`、认证、权限、支付、迁移、事务、外部合同）不能
在集成路径上 stub；替身只能放在隔离测试里，硬边界阻塞时停止合形、升级或串行等待。
起胚或合形暴露出原假设不成立时，直接改形，不要为了维护原计划继续加补丁。

每隔一段回看整体：演示、截图、端到端路径或完整调用。问一句：现在的形状还像用户要的
东西吗？如果不像，停下来调整，而不是继续抠局部。

## 打磨：按关注点提高分辨率，不是阶段门

整体成立后，再按关注点增加分辨率。通常一轮只选一个焦点；需要时可以合并，但不要同时
把所有关注点都打开。轮次按风险和当前证据选择，不要求全部走完；小任务可以压缩，高风险
任务可以重复某一轮。

| 关注点 | 目标 | 常见进入信号 | 退出证据 |
| --- | --- | --- | --- |
| 主路径 | 主要行为真实成立 | 整体能跑 | 主路径验收检查 |
| 边界 | 空、错误、部分完成、重复、权限、并发 | 主路径稳定 | 边界用例通过 |
| 结构 | 删除脚手架、重复和死代码，对齐接口 | 行为稳定 | 结构检查与回归 |
| 品质 | 性能、UI、可访问性、可观测性、文档 | 结构稳定 | 基准、真实画面或项目检查 |

这些是常见关注点，不是必须按顺序通过的阶段门。当前验收目标需要时，可以提前做必要的
结构、边界或性能工作；不要让轮次顺序阻塞主路径。

验收先于实现，但不强制红-绿循环。每个切片先写清观察点（seam）、输入、前提、可观察
结果和期望；期望值来自规格，不来自实现的复算。修 bug 或新增、改变行为时，新增测试要
能在原实现上失败；纯重构以改动前后的行为一致、特征测试、golden 输出或 API diff 验收，
测试应在重构前后都通过。不为了让测试变绿而改弱断言。TDD 只是让验收提前的一种方式：
seam 清楚、行为清楚、反馈便宜时可以红-绿；否则先立验收锚点，再实现，再补检查，但完成
前必须有可运行的验收；对于行为变更，它要能在原实现上暴露这次变化。

高风险改动按
[risk-driven-testing](https://github.com/lidessen/skills/blob/main/skills/risk-driven-testing/SKILL.md)
选择观察层，并让测试设计独立于实现。至少覆盖主路径、边界、依赖失败、部分完成、空输入
和重复副作用；断言公开行为和真实副作用，不测内部调用；替身只放在真实外部边界。高风险
或跨模块改动让测试设计者只看规格和接口，不看实现，避免用自己的实现假设给自己出题。

行为变更和重构分开提交。重构通常放在结构轮，不混进主路径或边界轮的 commit；如果它是
获得可测试接口或解除当前阻塞的最小前提，可以先做，并单独提交。局部已经稳定不代表可以
一直抠下去；当前轮达到退出证据就进入下一轮，或者停。结构轮需要整理残留和重复时，按
[defrag](https://github.com/lidessen/skills/blob/main/skills/defrag/SKILL.md) 处理。

## 保障剪枝：门禁要有预算

每加一道 gate、检查、交接或 review，先写清三件事：它拦哪种具体失败、为什么必须在这
里拦、删掉后谁接回保证。答不清就不加；能降级为提示或反馈的，不设成阻断。权限、事务、
不可逆副作用和真实合同是硬边界，不能以“局部取舍”为由跳过。

安全审查先看实际部署：谁能提供输入、进程持有什么权限、失败会伤到谁。本机单用户工具也
可能把凭据发错或误删数据，这类可达路径足以阻断交付。仅在多租户部署下才可达的风险，
记下触发条件，到开放该边界时再处理。主路径与硬边界已有证据后，下一步优先补真实运行中
仍缺的证据。复审聚焦尚未关闭的阻断项、刚改动的路径或新发现的风险。

验证通过是证据，不是新的流程层。同一证据不重复包装成 gate；互补证据（例如运行验证 +
独立审查）覆盖不同盲区时保留，但按新增覆盖和成本判断。失败先给修复报告，不要自动升级
成新域、新流程或新门禁。保障性代码和流程本身也要算成本：它们占用的注意力和维护量，
和它们防止的失败相比是否值得。需要审查已有保障机制是否过度时，用
[assurance-review](https://github.com/lidessen/skills/blob/main/skills/assurance-review/SKILL.md)。

## 验收与收束

交付前只保留一个权威实现。本次范围内的 stub、候选、临时重复和脚手架必须删除或替换；
范围外的后续工作写入现有 issue/日志，列为后续工作或未验证面，并在交付说明里单独列出，
不能把“以后再清理”当成已完成。

按项目已有方式运行 lint、类型检查、相关测试、全量测试和构建；优先跑与改动相关的检查，
声明了全量门禁或触及共享契约时再跑相应范围。完成报告列出实际运行的命令；没有自动检查
时写明“无可用检查”，并给出一个可执行的手工验收。机械检查通过不等于行为成立：改了
用户可见行为，要用真实调用、真实界面或运行证据核对主路径和边界。

`R2` 或不可逆改动还要有恢复证据：回滚或前滚方案、在一次性副本上演练、备份/恢复验证、
观察窗口和中止阈值；无法回滚时，在决策记录里写明原因和补偿控制。执行不可逆步骤前要
取得显式授权。`R2` 验收者的否决是约束性的，主 Agent 的最终验收不能覆盖；冲突升级给
人类 owner；没有人类 owner 时停止并报告冲突，不自行覆盖。

高风险或跨模块改动用 fresh context 做独立 review：只看任务、验收标准和 diff，不看实现
者的自我解释；review 结论要能落到具体位置和证据。最后明确说出未验证面，区分“读过”、
“检查过”、“测试通过”和“真实运行”。

界面改动必须对着实际画面验收，不能只看源码或信测试通过。需要更完整的视觉判断时使用
[interface-design](https://github.com/lidessen/skills/blob/main/skills/interface-design/SKILL.md)；
多页面持续打磨使用
[ui-improvement](https://github.com/lidessen/skills/blob/main/skills/ui-improvement/SKILL.md)。

项目惯例和本次任务授权包含提交时，本地提交是交付的一部分，不是实现之后另一次请示；
推送、打开 PR、发布或不可逆操作才需要明确授权。任务已授权继续开发时，本地提交、分支和
可逆检查点默认由执行者完成并记录；项目规范或任务明确要求提交前确认的，按项目规范。
交付说明做了什么、跑过哪些轮次、证据是什么、还有哪些假设和风险。

## 停止、转向与预算

同一思路连续 2 次失败且没有新增证据，或关键假设已被证伪时，换方案、换执行者或回到
定形；不要在同一错误上空转，也不要用更多门禁掩盖失败。每个未知默认给 15–30 分钟或
一次探索调用，到期输出事实、选项和可行/不可行；live/外部批次可以按一个批次周期计。

某条非硬边界工作线持续阻塞整体且超过预算，先 stub 并继续；硬边界阻塞时停止、升级或
串行等待，不适用这条。任务超出原范围时，拆分或重新定形，不要静默扩张。

上下文超过有效窗口 70%，或连续多次工具调用不改变判断时，交付已经成立的增量，说明缺口
和下一步，不把未验证说成完成。冗余的成本超过它的决策价值时，停止比较并选一个。剩下的
只有范围外的抛光时，停手，不要 gold-plate。

## 反模式

- 设计全部做完再实现，实现全部做完再测试；最后才第一次运行整体。
- 整体还没跑通，就开始抠局部细节、抽象和格式。
- 先写所有测试再写所有实现，测试针对想象出来的形状。
- 组一个没有明确 ownership、没有选择点、没有清理点的 Agent 团队。
- 在 `R1`/`R2` 或需要独立验收的改动上，让实现者自己写测试并自己判通过。
- 为了让测试变绿改弱断言，或把现有失败说成本次通过。
- 没有证据就说 done；把“代码写完”当成“任务完成”。
- 只写代码，不维护工作基线；或把工作基线做成官僚文档、第二份计划或日志。
- 只向下传步骤，不传目标；执行者不知道为什么做，遇到取舍就漂移。
- 把“超预期”当成范围扩张，或只做字面任务、发现方向错误也不说。
- 把完整日志、diff 或分析倾倒给人；一次要求人决定五件事；用“见上文”让人回忆。
- 在该请示的硬边界上擅自决定，或在授权内反复请示。
- 把通用方法当固定模板，照搬别的项目的文件名、命令或团队规模。
- 为凑“三人组”或“多 Agent”造角色。
- 用更多 reviewer、门禁或交接代替清晰合同。
- 每个失败都升级成新域、新流程或新 gate。
- 把“局部取舍”当成跳过权限、事务、迁移等不可逆边界的理由，或把硬边界 stub 掉继续。
- 环境改造变成平台瀑布，或在没有 before/after 证据时继续投入。
- 小任务写重流程，大任务省验证；两者都是把流程当成了目的。
- 用“早期/成熟”的阶段标签或项目年龄代替实际消费者、承诺与约束，去定兼容、迁移
  和测试投入。

## 完成条件

按任务风险取用，不是每次全部打勾；小任务只取相关项。

- 任务要求的行为已经成立；主路径和必要边界有可执行的验收证据。
- 任务说明和执行者都带着目标、边界和验收；不只是步骤清单。
- 本次范围内的 stub、候选和脚手架已经清理或转入 issue/后续工作。
- `R2`/不可逆改动有回滚、前滚或补偿控制，备份/恢复（适用时）和验收签署。
- 工作日志、决策记录、提交边界和项目本地工作基线已经更新，或检查后说明无需更新的
  理由。
- 需要人决定的事项已按 2–3 个决策点、约 500 字预算交付，每个决策点自足，有选项、
  后果和建议；授权内的事没有反复请示。
- 为流程而设的角色和门禁已经撤掉。
- 实际运行的检查已列出；没有自动检查时给出可执行的手工验收。
- 用户可见改动已经过真实运行或画面判断。
- 未验证面和假设已经写明。

达到这些条件就交付，不把已知缺陷留给下一轮，也不在范围外继续抛光。

本方法组织开发推进，不替代测试策略、设计判断和领域方法；需要时按上面的相邻技能接入。
