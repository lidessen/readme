# Capture

## 内容仓库

本仓库同时维护技能和内容：短想法直接写到仓库根目录的 `notes/`，文章写在 `blog/`。
这里的内容会公开，草稿和图片源码也可见；`_` 前缀只排除站点渲染，不是访问控制。
只写适合公开的内容，不把私人工作对话、原始输入或内部审校记录藏进 HTML 注释。
修改本仓库仍需当前任务具有写入授权，技能本身不授予目录权限。

## 目标

把用户提供的想法剪裁成可以直接展示在博客上的短想法，记录到本仓库的 `notes/` 目录，自动添加少量分类标签，并做一次轻量审校。这里的“纯想法”指去掉对话上下文和过程性填充，只留下核心观察、判断、疑问或感受；不是把它扩写成完整文章。

## 触发方式

当用户使用 `/capture <想法>`，或明确要求记录为博客短想法时使用本 skill。`<想法>` 是命令之后的全部内容。
开发讨论中的“记一下”、待办、设计记录和 skill 修改不触发；不要自行把它们公开为 Blog 内容。

## 工作流

1. 在已确认的内容仓库中使用 `notes/`，不要写入 `blog/`。
2. 先识别这段输入的核心想法：它可以是一个观察、判断、问题、假设或感受。去掉寒暄、对话指令、重复解释、无关背景和“我想让你记录……”等过程性内容。
3. 做适度剪裁和重组，使结果读起来像一条独立的博客短想法。保留用户的语气、第一人称、限定词和不确定性；不要为了完整而补充事实、论据或结论。若包含多个明显独立的想法，拆成多个文件。
4. 根据剪裁后的可见正文选择 1–3 个标签：

   - 第一个标签是较稳定的主题分类，后续标签可以描述更具体的对象或概念。
   - 先扫描 `notes/` 中已有 Frontmatter，语义相同时复用现有标签，不另造近义词。
   - 使用简短、自然、可重复使用的名称。中文概念优先使用中文；`AI`、`Agent` 等已经稳定使用的名称保留原样。
   - 不使用 `想法`、`随笔`、`未完成` 这类对所有内容都成立、没有筛选价值的标签，也不把整句话、临时项目名或未经正文支持的推断当作标签。
   - 无法确定细分类别时，选择更宽但准确的标签，不为了凑数量添加标签。

5. 为每条想法生成一个不引入新结论的简短标题，并新建一个 Markdown 文件。文件名使用本地时间和简短 slug：

   ```text
   notes/YYYY-MM-DD-HHmmss-short-slug.md
   ```

   slug 使用小写英文、数字和连字符；无法可靠生成时使用 `thought`，并通过时间戳避免重名。

6. 使用下面的结构。元数据记录 `created_at` 和 `tags`；时间填写捕获时的本地 ISO 时间，标签按“主题分类 → 具体概念”的顺序排列。正文只包含适合公开的想法；原始对话、审校过程和待确认问题只在当前回复中说明，不写入公共文件或 HTML 注释。
   ```markdown
   ---
   created_at: YYYY-MM-DDTHH:mm:ss+08:00
   tags:
     - 主题分类
     - 具体概念
   ---

   # 简短标题

   剪裁后的纯想法。
   ```

## 审校边界

- 可以修正明显的错别字、标点和语病，删除对话填充，合并重复表达，调整句序，并指出指代不明、句子断裂或内部矛盾。
- 剪裁后的正文要能脱离当前对话独立阅读，但只需达到“短想法”程度，不必补成论证完整的文章。
- 保留原文中的限定和不确定性，例如“可能”“我还不确定”；不要把猜测写成事实，把问题写成结论。
- 不做事实查证、深度分析、价值判断或文章扩写。
- 标签只描述剪裁后正文中确实存在的主题，不用标签替正文补充立场、来源或结论。
- 不把想法改写成计划、承诺、任务、结论或 acceptance criteria。
- 不因内容不完整而要求用户补充；把真正影响理解的缺口在当前回复中说明。
- 保留用户公开表达的意思；原始输入和内部审校记录不写进公共文件，也不擅自批量清理其他文章。

## 完成后的回复

简短告知用户已记录的文件路径和所加标签，并用一两句话概括做过的剪裁和审校。若没有问题，明确说“无明显问题”；不要在回复中重复整段想法。
