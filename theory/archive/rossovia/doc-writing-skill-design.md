## 要解决的问题

Agent 写 README、模块说明、设计文档时，产出的文本读者一眼能认出是模型写的：节标题套模板、每条列表加粗小标题、
形容词代替数字、每段结尾总结、面面俱到不表态、缺事实时用模板内容填满。现有 `post-review` 只处理本仓库博客文章，
风格样本是 `apps/blog/content/thoughts/`，不适用于面向他人的项目文档；它也不覆盖英文。

需要一个不依赖本仓库路径的通用 skill，同时覆盖中英文，供开发侧和其他项目使用。

## 理论：读者为什么读不进去，模型为什么写成那样

这一节保存第五、六版形成时的解释，不是独立维护的执行指令；第八轮已收回其中的篇幅阈值、固定句式和“少覆盖”要求，当前行为以 `SKILL.md` 为准。
这些解释来自五轮试验和三次用户指正，第五版 `SKILL.md` 按它重写。前四版是从症状出发积累规则，
每轮补一类；这一版先说为什么，规则从原因推出来。

### 读者一侧的四个约束

1. 工作记忆短。读者一次只拿着几件事，每读一句要把它挂到已有的某件事上（语言学里的 given-new 合同）。每句都是全新事实的
   文档没有落点，读者读几句丢几句。
2. 靠信号判断重要性。散文里能传递重要性的信号只有篇幅、重复（同一件事用后果、例子、数字再说一遍）、位置和明说的立场。
   每段等长、每句停在同一抽象层的文档把信号抹平，读者只能逐句自己判断。
3. 识别比生成便宜。读到一句例子，读者认出它在说上一句的事，用一下或跳过；读到省了主语的句子、当场造的缩略、跳过中间步骤
   的结论，读者要自己把省掉的部分生成出来。所以人类的“冗余”（往具体处走的复述，可识别）读起来是丢弃，模型的短而密读起来是重建。
   同一抽象层的复述（段末总结）不在此列：读者要比对一遍才能确定它没有新东西，比对本身是成本，这解释了“删总结、留例子”为什么不矛盾。
4. 已知的东西决定什么算 given。同一团队的设计文档和外部用户的 README，同样的事实该展开的地方不同；查阅型文档（RFC、man page）
   可以很密，因为读者不顺着读。所以“密度”本身不是判据，“密度随重要性变化”才是，读者是谁是调这个刻度的地方。

### 模型一侧的四个原因

1. 不感到读者成本。模型拿着完整上下文，每句全新对它没有代价，于是按覆盖写：一条事实一句，密度均匀，不分轻重。
   数据：人类中文说明文档每千字 0.6 到 2.7 处举例标记、段长离散度 0.77 到 1.16；前三版产物举例常为 0、离散度 0.4 到 0.7。
2. 缺维护者的材料。没有事实就模板填充，没有立场就对称平铺，没有具体读者就“无论你是初学者还是专家”。这是内容层痕迹的来源，
   翻译式的处理解决不了，所以 skill 保留“先拿材料”一步。
3. 输出预算。系统提示要求简洁，模型省功能词、用箭头和冒号标签代替句子、把规则写成格言、把段落写成提纲。最先出现在写作者
   自认“本来就该短”的位置：规则、标题、列表条目（本 skill 自己的“一句只推进一件事”“定位：翻译，不是去味”就是例子）。
   前几版反复说“删”，与这条压力同方向，把产物推向更密。
4. 语域习惯。偏爱的词、句式、标点、骨架，以及把一种语言的语法带进另一种。这一类的成本主要不是理解，是识别：读者认出是
   模型写的之后，对内容的信任跟着降。

前两条决定文档有没有东西、读者能不能读进去，后两条决定读者认不认得出。处理顺序先前两条。

### 由此推出怎么让 Agent 写出来

规则清单不改变生成。证据：`ai-patterns.md` 列出的痕迹，写进清单的同一天在 skill 自己的文本里又出现。所以 skill 的做法是把
读者的约束变成写作前和写作后的显式动作，而不是指望写的时候“注意”：

- 写之前：拿材料（事实、读者、立场），并写下读者必须带走的两三件事。轻重在动笔前决定，篇幅随之分配。
- 写的时候：每句从上一句已有的东西出发；机制后面跟后果、例子、数字，例子只能来自已给事实；规则、标题、条目也写完整句子；
  预算紧就少覆盖，不压缩。
- 写完：三遍自查，第一遍只看形状（段长是否有差别、有没有例子、有没有连续全新句），第二遍对照人类样本，第三遍逐条扫痕迹表。
  形状检查放第一位，因为它对应的是理解成本，而且模型凭感觉读不出来。
- 交付：说明里列出自己走的推论和缺的材料，把读者本来要重建的东西外化给维护者。

第六版补了一条在生成时起作用的手段。前面几条都是写前决定和写后检查，绕开了生成本身；用户指出这正是难点：表达习惯的惯性
和人一样大，要在生成时影响它，得有比规则强得多的“感染”。第七轮试了三种感染方式（读人类文本、扮演角色、按回复的口气起草），
结论是模型的语域跟着上下文里离得最近的文本走，所以最可靠的办法是动笔前把一两篇人类写的同类文档整篇放进上下文；角色只借
说话方式不借记忆；回复式起草作为一节写平了时的局部工具。细节见第七轮。

### 验证到哪一步

第 1、3 条模型原因有语料和试验数据支持。第 2 条读者约束（信号）在第六轮得到支持：第五轮加局部层次规则后举例和句长回到人类区间
而轻重指标未动，第六轮加“先定轻重”后节长离散度在三个任务上都上升、两个进入人类区间，与“局部层次和全局轻重是两件事”一致。
指标本身也修正过一次：轻重体现在节的长度，不在段的长度（见第六轮）。读者一侧的四个约束是从认知科学的常识和用户观察里拿来的解释，
本 skill 没有做阅读实验，“读者省力”仍然只有代理指标。

## 已接受的设计决定

### 名称与位置

`skills/doc-writing`。名字描述动作与对象（写项目文档），与 `concept-naming`、`structuring` 同一构词方式；
“去 AI 味”是方法不是对象，放进 description 作为触发词。放在通用库，因为它只依赖公开的开源文档样本，不依赖 Meowland 私有路径或角色。

### 核心判断：两层都处理，顺序从内容到词汇

第一版把 AI 味主要归到信息层（事实、读者、立场、每句的理由），把词汇和句式当次要症状。用户指出表达层的固定痕迹占读者反应的大半，
要求参照网上的吐槽补齐。查了维基百科 AI 清理小组的 [Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing)、
一份基于中文对照语料做频率统计的[去 AI 味实证手册](https://www.jxxy.net/ai/articles/voidJan-2095423973865746931/)、
[cn-humanizer](https://github.com/0xtresser/cn-humanizer) 等中文模式集，以及 [SlopDetector](https://slopdetector.org/blog/signs-of-ai-writing) 的阈值研究之后，
第二版改为两层并列：表达层（高频词、“不是 X 而是 Y”、三件套、句末 -ing 尾巴、破折号、提示性冒号、加粗、总分总）和信息层。
`ai-patterns.md` 重写为按词汇 / 句法 / 篇章 / 内容四层组织的诊断表，中英文各附词表，并加入“不能当判据”反表。

自查顺序从内容层往上：先核事实，再看结构，再看句式，最后扫词表。反过来会出现只换了词的假修好。词表的作用是让模型看见自己看不见的
习惯（自己写的东西最难察觉），不是让它逐词替换。

### 采纳外部研究时保留的判断

- 单项命中不是证据，叠加才是（维基百科和 SlopDetector 都这样声明）。
- 实证手册的“不能当判据”表与本 skill 自己的语料观察一致：问句标题、“X 是一个……”开头、正文里的“首先……其次”、名词化长句、
  重复全称，人类用得不比 AI 少甚至更多。这些进入硬约束，防止为了“更像人”制造新腔调。
- 词表随模型版本变化（delve 在 2025 年后少见），来源里的模型指纹只作参考；判断原则不随词表变。
- 模型指纹表显示 Claude 的中文输出破折号和过长前置定语偏多、“不是……而是”中等；这是本 skill 主要使用者的习惯，
  已在句法层单列。

### 把 skill 定位成翻译

用户读第三版 `SKILL.md` 后指出：它信息密度很高，怀疑那些不自然的表达正由此而来。人写的文档删掉冗余信息其实很短，
但正是冗余帮读者理解；模型文档句句新事实、没有密度层次的变化，读起来更累。量了一下（去代码块和表格）：
人类中文说明文档每千字 0.6 到 2.7 处举例标记（比如 / 例如 / 也就是说），skill 三份文件为 0，skill 组产物 0.75 到 1.35；
英文人类每千词 1.7 到 5.2，skill 组产物全部为 0，而第三轮 baseline 概念页还有 2.0；句均长度、“的”字比例、段长离散度
都是产物低于人类区间，且 skill 组低于 baseline。也就是说前三版让产物比 baseline 更密、更短、更齐。

原因在 skill 自己。“一句话如果读者读完不比读前多知道什么，删掉”是一条压缩规则，与输出预算同方向；举例、说后果、
换个说法复述，按这个标准都该删，而它们正是人类文档里帮读者的那一层（TiDB 讲 Raft 一个机制后面跟五层下降，
Django 每条原则“主张 → For example → 限定”）。只做减法会收敛到另一种 AI 味：密、齐、短。

用户由此提出重新定位：skill 的作用不是“去 AI 味”，更像翻译，把模型的表达译成人读起来舒服的表达。采纳。第四版 `SKILL.md`
改为两步：第一步拿到维护者才有的材料（事实、读者、立场），第二步把材料译成读者省力的形式；“AI 味”降为第二步没做好的症状清单，
只在 description 里作触发词保留。“每句的理由”一节改为“密度有层次”：删句子的标准从“不多知道什么”改成“既不增加事实也不增加理解”，
并正面写出该有的东西（机制 → 后果 → 例子；读者会问的问题直接答；重要处降三四层，次要处一句）。`ai-patterns.md` 篇章层新增
“密度均匀、层次不降”并附上述计数；“不能当判据”表加“举例、说后果、复述”。翻译定位只覆盖第二步；编造、对称平铺、
写出维护者不想暴露的实现名这类内容问题，翻译解决不了，所以第一步保留。

第四版写完，用户挑出两句：`SKILL.md` 里的规则“一句只推进一件事”，和本记录的小标题“定位：翻译，不是去味”。前者省了“话”，
“推进”是写作教程里的比喻动词，“一件事”没说清什么算一件，读者要自己展开成“一句话只说一个意思，机制和例外分两句”；
后者是冒号标签、“不是 X”对比，加当场造的缩略“去味”，三个 `ai-patterns.md` 里列着的痕迹挤在七个字里。两句都出现在写作者
自认“本来就该短”的位置：规则和标题。模型进入写规则、写标题的模式时切换到格言体，人类写指导文档（Effective Go、Django）
仍是完整句子加例子。所以压缩最先出现在规则、标题、条目，而不是像第四版写的“长文后半”；而且这些痕迹是在写进清单的同一天
又用上的，说明清单只能事后逐条对照，不改变生成。第四版据此重写了 description（原来是四个四字格并列）、所有小节标题
和“写句子的时候”一节的每条规则，规则写成对读者说的完整句子并带适用情形；`ai-patterns.md` 电报体一节记下这两个例子。

用户接着指出规则里的例子“‘具体参数可能需要根据实际情况调整’换成‘熔断 5 分钟是拍的，上线后看指标调’”改前能懂、改后看不懂。
改后那句依赖 Webhook 事实清单的上下文（熔断）、用了圈内口头语（拍的）、又压缩（看指标调），三个都是 skill 自己列的问题；
它在原设计文档里成立，是因为前文定义了术语、读者是同一个团队，搬进 skill 当例子这些支撑都没了。同类问题还有 `human-samples.md`
把试验事实清单里的句子（“阈值是拍的”“`touch` 不会触发上传”“一个用户报告能用”）当成人类样本的观察引用。
已全部换成自含的例子或语料里的真实引文（Go “if the stars align”、Redis “best effort”、ripgrep “won't search files ignored by
your .gitignore”），并在规则里加一句：例子和引文要读者不需要背景就能懂。

同一版顺带处理了上一轮自审 review 出的问题：description 与正文对翻译的说法矛盾；“第一句就出戏 / 第二段出戏”是假精确；
“长文后半会压缩”从事实改回用户观察；触发列表里的“变更说明”没有对应指导，删掉；例句“6 个实例各自限速”改成自含的版本；
“修订已有文档”三类改为形式 / 无来源 / 疑似错误；加粗段首小标题改成小节；“X，不是 Y”从约 8 处减到 1 处例外说明；
“不要用这个如果……”改回中文语序；delve 换成当前仍常见的词；免责式结尾删掉。

### 压缩与翻译腔纳入纠正范围

用户观察到两类此前没覆盖的来源。一是输出预算：系统提示要求“简洁”“少输出”时，模型会用不常见的压缩表达省 token，
很多刺眼的句式和短语由此而来，长文后半尤其明显。二是跨语言：翻译时过度翻译（把 issue、token 译成“议题”“令牌”），
或者用英文习惯写中文、用中文习惯写英文。第三版把两者写进 `SKILL.md` 的句子规则和自查清单，`ai-patterns.md` 句法层
新增“电报体压缩”和“翻译腔（两个方向）”，`language-notes.md` 补了过度翻译的语料计数（26 篇里 issue 126 次对“议题”0 次、
token 129 对“令牌”0）、英文习惯写中文的六条症状、中文习惯写英文的七条症状和翻译任务的处理方式。

这一条也修正了 skill 自身的一个风险：前两版反复说“删”，与输出预算叠加会把写作者推向电报体。现在明确“删”指删没有信息的句子和节，
不指句内的主语、连词、冠词和虚词；真有长度限制就少覆盖内容，句子仍然写全。翻译的范围也随之调整：原先整体排除翻译，
现在翻译只用语言部分，结构、事实和立场跟原文，不套用重写权限。

### 用真实样本校准，而不是描述“自然”

`human-samples.md` 提供可对照的上游文档链接和观察到的特征，要求写完后与同类样本并排读开头、中段和结尾。
样本选取偏向说明口吻（单维护者 README、RFC、FAQ、最佳实践），并明确指出推广型 README（阿里、Dromara 系的部分项目）
和企业维护 README（Redis、Vite）最接近 LLM 节奏，不作为校准目标。

### 渐进披露

- `SKILL.md`：触发、两层 AI 味、四个信息层判断、结构与句子规则、两遍自查、修订已有文档的三类处理、交付。
- `references/human-samples.md`：样本表与共同特征。
- `references/ai-patterns.md`：按词汇标点 / 句法节奏 / 篇章结构 / 内容四层列痕迹、占位物和改法，附中英文词表、“不能当判据”反表和来源。
- `references/language-notes.md`：中文（混排、翻译腔、人称、少见写法的语料计数）与英文（voice、具体性、标点、少见词计数）各自的习惯。

## 语料与观察

英文 22 篇：esbuild、ripgrep、fzf、tokio、htmx、caddy、redis、bun、pytest 的 README；Go loopvar 提案与 TEMPLATE、Rust RFC 1105、
Kubernetes KEP 模板与 sidecar KEP；Django design philosophies、curl CONTRIBUTE 与 connection filters、git gitworkflows、
Effective Go、PostgreSQL MVCC、SQLite “Appropriate Uses”、Vite “Why”。

中文 26 篇：Ant Design（README、介绍、设计价值观、贡献、FAQ）、Vant（README、快速上手、进阶、贡献）、TiDB（概览、架构、最佳实践）、
RocketMQ（架构、设计、最佳实践）、阮一峰 ES6（简介、let）、Sentinel 介绍、Dubbo 介绍、Arthas、Taro、Nacos、Hutool、MyBatis-Plus、
Sa-Token 的 README；VitePress 中文作为译文对照。

由两个独立 sub-agent 分别做定量观察，主要结论已写入 references。值得记下的几点：

- “X is a…” / “X 是一个……” 开头在两种语言里都是最常见的人类写法（英文约半数，中文 12/26），不是 AI 味；第二句立刻给版本、平台等具体事实。
- 英文 22 篇约 14,600 行里 “In conclusion”“Key Features”“seamless”“delve” 为 0，“In summary” 1，“It's worth noting” 3；16 篇没有任何 em dash。
  加粗小标题列表出现在 6 篇，集中于企业 README。
- 中文约 9 万字里 “综上所述”“值得注意的是” 各 1 次且都在承接真实内容，“本文将”“赋能”“不仅……而且” 为 0，“暂无计划” 为 0（维护者写“不支持”“无法”加版本号）。
  说明型正文里感叹号为 0。
- 中英文空格分两派（前端/数据库文档加，Java 系不加），“您/你”在人类文档里也混用，“的”密度说明型高于推广型——这些原本容易被当成 AI 判据的形式特征不成立，已在 `language-notes.md` 中按语料修正。
- 人类样本保留拼写错误、TODO、旁白和不对称的篇幅分配；模板里没有内容的节留空或写 “None.”。
- 设计说明有两种推进方式：提案类按问题 → 方案 → 被否方案 → 未决；架构/最佳实践类按机制 → 后果 → 建议。都先给真实代码、数字或事故。

## 试验方法

按 `agent-guidance` 的评估要求做 baseline 与 treatment 对照：相同任务、相同材料、相同权限，一组不加载 skill，一组先完整读 `SKILL.md` 再工作。
每组一个新的 sub-agent，无对话历史。产物写到 `/tmp/trial/`，不进入仓库。主 Agent 对照语料观察逐项比较，不打分。

任务材料是带有明确空白的事实清单（“没有基准”“R2 有一个用户报告能用，未测”“阈值是拍的”），用来观察是否编造、是否把未知写成已知；
另有一个真实仓库任务（为 `packages/go/providerconfig` 写中文 README）观察需要自行取证时的行为，以及一份人为写成典型 LLM 风格的中文 README 用来观察修订能力。

## 第一轮（skill 第一版）

任务：英文 README（事实清单）、中文设计文档（事实清单）、中文包 README（真实代码）。

观察：

- 两组都没有编造事实清单之外的数字和承诺；受约束的事实清单本身已经压住了最严重的 AI 味。差别集中在结构和立场。
- 英文 README：baseline 用 10 个节、2 张表、4 条加粗小标题列表；skill 组 7 个节、无表、无加粗小标题，多了 “When not to use it” 一节和 “Run with `--dry-run` first” 这类替读者做的判断，开头两段与 esbuild/ripgrep 的开头方式一致。
- 中文设计文档：baseline 编号七节、补了一节事实清单里没有的“目标”、被否方案用表格；skill 组小节标题写成主张（“限速维度是目标域名”“连续失败 20 次后熔断 5 分钟”）、被否方案用段落、在代价处直接写“如果评审认为应该反过来……这里是要讨论的点”，并从事实中找出两个清单没写明的未决点（探测失败后的行为、限速延迟是否消耗重试次数）。它的交付说明还指出事实清单本身的一个逻辑漏洞：
  “按客户限速解决不了 40 个订阅指向同一域名”这条理由不成立，因为同一客户的 40 个订阅在按客户限速下总量会被限住；文档按清单复述，说明里留给维护者确认。
  这是 skill 要求的“读者是可能反对的评审者”产生的行为，不是清单设计的一部分。
- skill 组两处偏移：一是做了一步推论（“总量是 6 倍单机额度”“rebuild 不会触发上传”），虽可从事实推出但清单没写；二是中文设计文档口语偏重（“扛不扛得住”“买单”）。
- 中文包 README 的 baseline 已相当接近本仓库其他 README 的密度和口吻，说明仓库 `AGENTS.md` 本身已经在约束表达；这个任务对 skill 的区分度低。

据此修订：明确“推论只走一步且读者能用文中事实验证”；“口语程度跟随项目已有文档，不为显得像人刻意口语化”；“短句是偶尔的锚点”；新增“修订已有文档”一节，把无来源主张分成可删的形容词、需保留并标注待确认的实质主张、需单独指出的疑似错误三类。

## 第二轮（修订后）

任务：英文设计文档（事实清单，含未询问的干系人和未测的估计）、修订人为写成 LLM 风格的中文 README（无源码可核）。
另有第一轮的中文包 README skill 组产物在本轮一并比较。

观察：

- 英文设计文档：baseline 是 Status / Summary / Current state / Problem（表格）/ Proposal（三个子节全为列表）/ Alternatives（加粗小标题）/
  Costs（加粗小标题）/ Open questions，形状接近 KEP 模板填空，且把已在 Costs 写过的两个未知重复列进 Open questions。
  skill 组开头一段直接写决定，第一个小节标题是主张（“Six of the seven YAML bugs were valid files with the wrong meaning”），
  被否方案和代价用段落，写出“The panic at least failed loudly”“that is your check before you delete the old file”这类替读者做的判断，
  并把“没问 CI runner 维护者”的后果说清（“the 3 runners need an answer before the removal release, and this proposal doesn't have one yet”）。
  两组都没有编造。skill 组两处可议：用通用 TOML 知识解释为什么两类 bug 消失（事实清单没有，但读者可核）；
  “What changes” 一节用了四个加粗段首小标题，是加粗列表的段落版。
- 修订 LLM 风格 README：baseline 删掉了 emoji、口号和收尾，但把无来源的形容词升级成了断言（“热路径上不做额外分配，适合高并发场景”“避免字符串拼接”），
  并整张删掉性能对比表——回复里提了一句“若有 benchmark 数据可以补回来”，文档本身没有留下“没有基准数字”的痕迹。skill 组把特性列表里能落地的事实并进开头一段，性能对比表改写成“与标准库 `log` 及其他日志库的对比目前没有基准数字。已有生产环境使用。”，
  路线图改成“尚未实现”，并在说明里列出需要维护者确认的主张。这是两组差别最大的任务：skill 的“无来源主张不删不美化、改中性并标注”规则被执行了。
- 中文包 README（第一轮 skill 组）：比 baseline 多核实了 flock、备份改名、`WORKCELL_PROVIDER_CONFIG`、CLI Runner 拒绝等接线事实，
  加了“不做的事”一节和一条加粗警告（“`provider.json` 存在就会选 Pi”）；抽查 `go 1.27`、`.meowland.lock`、`provider-backup-*` 三处与源码一致。
  这类任务上 baseline 已受仓库 `AGENTS.md` 约束，差别主要在读者视角，不在词汇。

据此修订：`ai-patterns.md` 增加“加粗段首小标题成为默认节奏”一条；`SKILL.md` 说明通用领域知识可用于解释但要写成可核对陈述，不顶替项目自己没做的测量。

## 第三轮（表达层重写后）

前两轮的事实清单写得很紧，事后用词表脚本回扫，baseline 和 skill 组在词汇层痕迹上都接近零；那两轮实际只测到了结构和立场，
没有测到表达层。第三轮改用口头交代式的松散简介，给写作者发挥空间：中文“为什么有 cfgcheck”说明页、英文 relay 概念页。
同时用一个简单的正则计数脚本（词表、破折号、“不是……而是”、加粗小标题、冒号引列表、条目数、句长离散度）辅助比较，不当作评分。

观察：

- 中文：两组词汇层都干净。baseline 用了两处加粗段首小标题（“**JSON Schema。**”“**CUE。**”）、9 条列表；skill 组零加粗、4 条列表，
  多写了一句一步推论（“如果启动时有一条规则，这个 0 在服务起来之前就会变成一条错误”）。baseline 结尾的“适不适合你”一节是替读者做的判断，
  写得不差。两组差别小，这个任务对 skill 区分度低。
- 英文：baseline 6.5 KB、skill 3.6 KB。baseline 有 2 处 em dash、4 条加粗小标题列表、16 条列表、5 处冒号引列表、一张表、一份 checklist、
  一段 ASCII 图，“**at least once**”这类正文加粗；skill 组零加粗、零列表、零破折号，全部段落。信息覆盖两组一致。
- skill 组一处判断失误：简介说“底层是 NATS JetStream，用的人不需要知道，我们不希望他们依赖它”，skill 组仍写出了 JetStream 的名字并加一句“别依赖”；
  baseline 写成“构建在某个 broker 上，具体是哪个有意不纳入契约”。skill 组的交付说明表明这是有意为之（“读者迟早会发现，点名是为了让他们发现后不去依赖”），
  理由能自圆其说，但维护者已明确表态时不该由写作者替他们改主意。这是 skill 对“事实”的强调压过了对维护者意图的判断，
  已在 `SKILL.md` 读者一节补一句：事实真实不等于该写。同一份说明还指出简介里“up to 5 times”没说清是 5 次重投还是共 5 次投递，
  属于评审者会问、简介没覆盖的点。
- 本模型的 baseline 在文档任务上本来就很少产出 delve / robust / 赋能这类词汇层痕迹；它的痕迹集中在格式层（加粗、列表、破折号、checklist、表格）。
  词表对本模型的价值主要在修订其他来源的文本，以及供其他模型使用这个 skill；格式层规则对本模型直接有效。

## 第四轮（压缩与翻译规则加入后）

三个任务，每组一个无历史的 sub-agent，baseline 不读 skill。

- 中文设计文档，任务开头加一句“【运行环境要求】回复务必精简，尽量减少 token 输出”，事实清单与第一轮相同。
  baseline 变成提纲：16 个标题（1.1、2.3 三层编号）、21 条单句列表、12 处加粗、被否方案排成表格，全文没有一段把机制和后果连起来说；
  “延迟时间 = 当前桶预计恢复时间”照抄了清单里的等号。skill 组 7 个标题、3 条列表、0 加粗，全部段落，等号写成“等于”，
  并补了一步可核的推论（“接收端恢复后，积压的重试和新事件一起受每域名 50 请求/秒的限制”）。两组总长接近（1586 对 1469 字），
  说明“精简”要求两组都执行了，差别在于压缩落在哪里。这轮没有出现箭头、缩略语这类词级压缩；本模型在文档任务下的压缩形态是提纲化，
  已回写进 `ai-patterns.md` 作为篇章级的首要形态。skill 组另加了一条清单里没有的未决定项（探测请求失败怎么处理）；任务允许写成未决定，
  这属于评审者会问的缺口，与第三轮的“up to 5 times”同类。交付说明里还指出灰度到 1 个实例时另外 5 个实例仍不限速、域名总量在灰度期间实际不受控，
  以及“Redis 不可用”如何判定；这些都没写进文档，留给维护者。写作者自述“任务要求精简，按 skill 少加内容但句子写全”。
- 英文 → 中文翻译，源文是 ripgrep README 的三节（708 词）。baseline 已经不差，差别在从句处理：baseline 保留英文结构
  （“其他搜索工具所服务的许多使用场景”“这使得可以在模式中使用环视”“仍然存在某个本 README 未列出的、你所依赖的其他功能”），
  skill 组拆成并列短句按事件顺序排。baseline 把 “less supported decompression” 误译为“支持较少的解压格式”，skill 组译对（“解压其他不常见的格式”）。
  两组都保留了 look-around、SIMD、glob、PCRE2，没有过度翻译；“换句话说”两组都照译了 “In other words”。
- 中文 → 英文翻译，源文是 TiDB 最佳实践的“场景与实践”（1647 字）。baseline “It is recommended to” 6 次、
  “In addition / However / As mentioned above” 起段 3 次、逗号并列句 6 处；skill 组改成 “We recommend” 和祈使句、连接词 1 次、逗号并列句 3 处。
  两组都把“极具亮点”译成 “performance is a real highlight”、“非常方便”译成 “very convenient and easy to use”，
  是把评价性习语译成了意象。skill 组在交付说明里点出这两处是原文的推广口吻、按规则照译不改，说明“原文的问题指出但不擅自修”这条被执行了；
  译法本身的问题（意象而非判断）和 “It is recommended” 已补进 `language-notes.md` 的英文部分。英译中的 skill 组补了主语“我”（原文省略，
  后文 “my blog” 表明单人维护者），并提醒相对链接仍指向英文文件；两者都是翻译任务里该由维护者确认的项。

这轮的结论：压缩规则对提纲化有效，词级压缩在本模型上没触发，对其他模型未验证；翻译规则带来的是从句重排和连接词减少这类中等幅度的改善，
baseline 翻译本身的水平限制了区分度。

## 第五轮（翻译定位与密度规则加入后）

重跑三个已有 baseline 的任务，看密度指标是否回到人类区间：第三轮的中文说明页和英文概念页（松散简介），第四轮的加“精简”要求的中文设计文档。
写作者读到的是第四版加密度规则之后、规则改写成完整句子之前的文本。

| 指标                  | 人类区间            | 中文说明页 v3 → v5 | 中文设计文档 v3 → v5 | 英文概念页 v3 → v5 |
| --------------------- | ------------------- | ------------------ | -------------------- | ------------------ |
| 举例标记 / 千字（词） | 0.6–2.7 / 1.7–5.2   | 1.35 → 3.33        | 1.05 → 1.31          | 0 → 2.58           |
| 句均长度（汉字 / 词） | 23–57 / 16–25       | 22.4 → 29.3        | 20.8 → 24.7          | 15.5 → 17.4        |
| “的”占汉字比例        | 3–6%                | 3.5 → 3.7          | 3.8 → 3.7            | –                  |
| 段长离散度            | 0.77–1.16 / 0.6–1.5 | 0.68 → 0.60        | 0.43 → 0.57          | 0.53 → 0.51        |
| 篇幅                  | –                   | 740 → 1200 字      | 956 → 1531 字        | 623 → 776 词       |

举例标记和句长三个任务都进了人类区间（中文说明页的举例略高于上限）；段长离散度没动，仍低于人类，说明产物段落还是偏均匀。篇幅增加 25% 到 60%。

读产物本身：新增的句子基本都是后果和例子，而且来自简介里已有的事实。中文设计文档补了“12 万次投递按 50/秒要排大约 40 分钟”“6 个实例共用同一个桶，实例数增减不影响总量”“对照第一次事故：……积压的任务按每秒 50 个放出”；英文概念页补了 “A message that fails five times leaves the original topic within about three minutes”“At the 1 MB maximum it is about ten thousand messages”，以及对每个机制的 “what this means for you”；中文说明页把“panic 或静默默认值”展开成两种暴露方式并把事故归到第二种。这些都是一步可核的推论。可疑的一处：英文概念页写 “some of the rest are exactly this kind of accident”（40 个 topic 里没用的一部分是拼写错误造成的），简介只说拼写错误会造出空 topic，没说现有的空 topic 有多少是这样来的；有 “some” 兜着，但已经在推论边缘。表达层痕迹三份都是零（破折号、加粗、箭头、-ing 尾巴）。

三份交付说明都主动列出了自己做的推论，和上面读产物时标出的完全重合（40 分钟、三分钟、一万条、“some of the rest”），
并请维护者确认；英文写作者还说明 version/timestamp 的例子是通用建议而不是 relay 行为。中文设计文档的写作者指出清单本身的一个矛盾：
任务队列也在 Redis 上，Redis 完全不可用时 worker 根本取不到任务，“放行不限速”只能对应部分故障（Lua 超时、主从切换）；正文按清单原样写，
问题留在说明里。这与第三轮“up to 5 times”、第四轮“灰度期间另外 5 个实例不限速”同类，是第一步（拿材料）在起作用。

“精简”要求那份，篇幅从 956 涨到 1531 字。任务同时要求覆盖全部事实，skill 说的“少覆盖内容”没有余地，写作者选择了写全；这符合规则，但也说明在“必须全覆盖”加“务必精简”的矛盾要求下，skill 会牺牲精简。

## 第六轮（第五版：理论重写，“先定轻重”与 given-new）

同样三个任务重跑。要验证的是理论一节的预测：全局轻重是不是和局部层次不同的一件事，“先定轻重”能不能把它拉出来。

先纠正一个指标。第五轮用段长离散度衡量轻重，这轮三份产物的段长离散度是 0.68 / 0.62 / 0.31，比第五轮还低或持平；但三位写作者的
交付说明都明确写了把篇幅放在哪几节（“Topics、Delivery、Ordering 长，因为那是团队被咬过的三处”“方案和熔断展开最多，
被否方案和实施各一句”）。按节算就看出来了：

| 节长离散度（cv）         | 人类样本               | baseline | v3 / v4 | v5   | v6（第五版） |
| ------------------------ | ---------------------- | -------- | ------- | ---- | ------------ |
| 中文说明页               | 0.39–1.12（中文 6 篇） | 0.32     | 0.45    | 0.48 | 0.53         |
| 中文设计文档（精简要求） | 同上                   | 0.50     | 0.45    | 0.67 | 0.81         |
| 英文概念页               | 0.77–1.64（英文 5 篇） | 0.41     | 0.38    | 0.35 | 0.54         |

三个任务都往上走，两个进了人类区间的下沿。最长节与最短节之比：人类 4 到 98 倍，v6 是 8 到 9 倍，baseline 4 倍。
人类在节的层面表达轻重，段的层面反而没那么参差；产物在 v6 也是这样。`SKILL.md` 的形状检查已从“每段多长”改成“每节多长”，
并给出十倍这个参照。

举例标记和句长维持在第五轮的区间（中文说明页举例从 3.33 回到 0.99，英文 2.87；句长 25 / 27 / 16）。篇幅比第五轮略短或持平，

交付说明的变化：三份都单列了“替读者做的轻重取舍”，并把推论逐条列出（英文概念页列了六条，含把 “up to 5 times”读成 5 次重投的解读）；

最新原稿如下，展示前未由主 Agent 润色。

### 接收重复通知

接收通知时，接收方需要按通知中的 `event_id` 去重，避免重复处理同一事件。接收方返回 2xx 即表示确认；发送方等待 5 秒，未收到 2xx 就会重试，最多重试 3 次。同一事件在重试时保持相同的 `event_id`。即使接收方已经处理成功，确认响应也可能丢失，因此再次收到通知并不意味着上一次处理失败。

### 修改配置后生效

修改配置后需要重启服务。服务只在启动时读取配置，没有热加载功能；磁盘上的文件发生变化，不会改变现有进程使用的配置。重启时如果发现配置格式错误，服务会报错并退出，不会自动采用默认值继续运行。

两版都覆盖所给事实，没有增加存储去重方式、热加载或恢复承诺。新旧差别主要是句序和措辞，
尚未观察到清晰的可读性提升；不再根据同一份小样继续堆规则，先把最新原稿交给用户判断。
快照和两版原稿保存在本机临时目录，此处已保留最新全文与材料范围。
`git diff --check` 通过；本轮未重新尝试仍缺原生绑定的 oxfmt，也未运行产品测试。

### 用户反馈：成熟术语本身可以降低理解成本

用户追问“热加载功能”是否就是热更新。主 Agent 随后建议改成“服务只在启动时读取配置。
修改配置文件后，需要重启服务才会生效”，用户指出“配置热更新”更直观、表达力更好。
这里的缺口是原稿术语不够准确，不是读者不理解术语。把熟悉的概念拆成长解释，反而失去
读者已有的理解入口。已在 skill 的术语规则中补明：优先选读者熟悉的准确叫法，需要时再解释
操作后果；不把短、抽象或使用术语本身当成问题。

据此局部修订的最新配置段如下。这是依据用户反馈的编辑，尚未进行新的独立作者试验：

服务不支持配置热更新，修改配置后需要重启。重启时如果发现配置格式错误，服务会报错并退出，不会自动采用默认值继续运行。

位置排斥复述的表达，判断回到具体阅读作用。历史记录中的“重复”观察不自动等于质量缺陷。

## 自审（用 skill 审 skill 自身）

按 `SKILL.md` 的两遍自查过了 `SKILL.md` 和三份 reference，用同一个正则脚本回扫，并把 reference 里引用的数字逐条对回来源（本地语料重新计数，
维基百科页面和中文对照手册重新抓取）。发现并改了三类问题：

- 无来源或核不上的数字。`SKILL.md` 开头“这一层占了读者反应的大半”没有来源，删掉。`language-notes.md` 写中文语料“约 9 万字”，
  重新计数是汉字约 4.7 万、总字符约 21 万，两个数都对不上原说法，改成可复算的汉字数；“It's worth noting 3”实际是 2（“worth noting”共 4），改正。
  `human-samples.md` 的“12 篇以‘X 是一个’开头”“约 100 个列表、18 个超过八条”按脚本重数是 11 到 12 篇、88 个列表、13 个超过八条，
  改成重数后的值并注明计数依赖切分方式。
- 把来源说错。`ai-patterns.md` 把中文对照手册里“一行以冒号结尾接列表”的 9.4 倍写成了整个“提示性冒号”的倍率，实际“核心是：”那类是 3.8 倍，拆开写。
  “有人把它叫翻案腔”是无源引用，改为指向中文对照研究并补 3.4 倍。is/are 下降 10% 一句写成“2023 年后”，来源说的是 2023 年当年，改正并注明出自维基百科指南引用。
- 自己犯的表达层痕迹。`SKILL.md` 两处、`language-notes.md` 一处破折号换成冒号或分号；`ai-patterns.md` 讲“不是 X 而是 Y”的那一节，改法本身就用了“不是……而是”，
  重写为正面陈述；“为抽象概念穿衣服”这个喻体换成直说。`ai-patterns.md` 开头整段复述 `SKILL.md` 的两层说明、`language-notes.md` 末尾“两种语言共有的”
  一节四条全部与 `SKILL.md` 重复，前者改成一句指回，后者删掉。长前置定语的例子在两份 reference 里各写一遍，保留 `language-notes.md` 的，另一处指过去。

没改的：四份文件都用加粗段首小标题分段（“**事实。**”“**混排与标点。**”）。这是 `ai-patterns.md` 自己列的痕迹，但同一节写了例外“读者要跳读的独立主题可以这样标”，
这些段落正是给 Agent 跳读的独立条目，按例外放行；语料里加粗小标题集中在企业 README 这一观察针对的是列表条目。`SKILL.md` 结尾“它是否被读者接受，
由维护者和读者判断”是范围说明，保留。自审的限制和试验一样：审的人是写的人，且是同一模型；这轮只能证明 skill 的检查表对自己的文本能执行，
不能证明结果对读者更自然。

## 证据等级

按 `agent-guidance` 的分级：`format-valid`（oxfmt、相对链接检查通过）；`behavior-observed`（十六个任务上 skill 组都出现了目标行为：
结构随内容、替读者做判断、无来源主张改中性并标注、格式层痕迹消失、精简要求下仍写段落、翻译时按目标语言重排从句、
密度规则加入后举例与句长回到人类区间、轻重规则加入后节长离散度上升）；`matched-improvement` 只在同模型、单次、无人工盲评的条件下成立。
`boundary-supported` 和 `regression-supported` 在前七轮未做。以上是前七轮的证据声明；第一版曾记录为 `adopt`，当前处置已改为 `adapt-and-retest`。第八轮的观察与限制单列在上文，不据此宣告整个 skill 有效。

## 前七轮的限制与未验证（历史快照）

- 试验中的 baseline 和 treatment 是同一模型，且 treatment 由同一模型读自己写的 skill；这检验的是 skill 能否改变行为，不能证明产物对人类读者“像人写的”。
- 每个任务每组只跑一次，没有重复；观察到的差别可能部分来自采样波动。
- 词汇层词表没有在本模型的 baseline 上触发过，所以“skill 能压住词汇层痕迹”对本模型未被验证；对其他模型或修订外来文本的效果未试。
  词级压缩（箭头、缩略语、标签句）同样没在本模型上触发，那部分规则来自用户观察，未经试验。
- 表达层词表来自第三方观察和统计，本 skill 没有复算它们的频率；采纳时只保留了与自己语料观察不冲突的部分。
- 语料观察由 sub-agent 完成，主 Agent 抽读了部分样本核对；自审时用脚本重算了 reference 里引用的计数，
  其余定性观察（“先说 why”“限制单开一节”等）仍未逐篇复核。
- 未做“负触发”试验（例如博客文章、营销文案是否被误吞），也未在其他模型上试。
- 密度指标是自己定的代理量（举例标记、句长、“的”比例、节长离散度），样本每种语言 5 到 10 篇；它们进了人类区间不等于读者觉得省力。段长离散度始终低于人类，但人类样本的轻重也主要体现在节而不是段，这个指标可能本来就不该用。
- 中文句长在七轮里始终停在 20 到 25 字，没有任何规则或感染方式把它推向 TiDB、RocketMQ 一类 39 到 40 字的说明文档；
  这可能是模型的惯性，也可能是本 skill 的 given-new 规则（一句只说一个意思）与长句本身有张力，尚未分辨。
- “读两篇人类文档”在试验里读的是本地语料副本；实际使用时 Agent 要从项目自己的文档或上游链接取文本，链接会失效，取不到时这一步就落空。
- 没有用户验收。skill 是否真的减少了用户改稿量，要看真实任务。
