# Project Sweep · 项目巡查整改

本项目内部开发技能。先看清结构，再沿结构逐块检查、整改和复验，最后核对各块如何组成整体。
专项目标决定本轮重点，通用质量检查随每块一起进行；既不能只搜已知问题，也不能把整顿变成漫无边际的重构。
用户只要求巡查时交付核实后的发现；要求整改时继续完成授权范围内的修复与验证。

代码组织、依赖、废弃清理和检查规则统一从[项目健康养生指南](../../../docs/maintenance/README.md)
按本轮范围选读；本技能负责巡查方法，不另维护一份项目规范。

## 先梳理真实结构

从用户目标确定范围、必须保留的行为和完成依据。读取根及局部 AGENTS、相关模块说明与实际入口，
梳理职责、公共能力、消费者、依赖方向、状态所有者和关键使用路径。目录只是线索，不等于责任边界。
设计说明目标，源码说明实现；两者不一致时核对迁移状态，不拿现状自动充当标准，也不把历史设计当现行要求。

形成一份足以指导检查的简图或分层清单：有哪些块、各自负责什么、共享什么、如何连接、依据在哪里。
不用先画完整仓库架构；范围清楚的部分即可开工，未知关系继续补查。明确排除项和原因，不能暗中缩成抽样。
例如 UI 整顿可以梳理为主题与基础组件、页面组合、动态交互入口和业务接线；这些是示例，不是固定分层。

## 按职责分治，并保留接合责任

把范围拆成可独立检查、整改和复验的块，再在块内逐项展开。共享根因和强耦合行为一起处理，
不要按文件数均分。每块说明对象、职责依据、专项重点、公共依赖、相关入口及验证方式。
公共层与消费者、跨模块状态交接和完整用户路径也要有人检查，不能成为各块之间的无人区。

分治不要求多 Agent；可独立推进且收益明确时使用 [divide-and-conquer](../divide-and-conquer/SKILL.md)。
该技能负责实际委派、共享写入归属与整合，本技能负责巡查整改的方法。无并行条件时按同样结构串行推进。
委派保留共同目标及通用、专项两类检查要求，不能一组只看专项、另一组泛看质量后就假定每块均已覆盖。

从入口和实现双向清点：范围内的入口能追到实现，实现能追到消费者或说明未接入/历史用途。
UI 应包括页面、弹层、动态 Surface、条件分支和不同控件用法；公共组件合同可共用检查结果，
消费者的事件绑定、样式覆盖和实际效果仍逐项核对。同构列表项可归组，不同状态与行为不能被默认项代表。
搜索命中和文件列表只帮助发现对象，不证明覆盖完整。

## 每块同时查通用问题和专项问题

围绕同一对象与使用路径，把两类判断合起来。通用检查是跨领域的质量问题，不仅指公共组件。
按该块的实际职责采用下列视角，不给每个文件机械套全套风险清单：

| 通用视角   | 要回答的问题                                                               |
| ---------- | -------------------------------------------------------------------------- |
| 职责与依赖 | 实现放在正确位置吗？公共能力是否被绕过或重复？业务状态是否泄入底层？       |
| 行为与合同 | 正常、边界、错误、取消或恢复等适用路径是否一致？错误是否到达正确处理者？   |
| 简洁与维护 | 有无失效分支、残留接线、无必要抽象、逐案补丁或过严门禁？已有机制能否解决？ |
| 事实与资源 | 状态是否重复维护？相关权限、持久化、幂等、并发和生命周期是否守住原有边界？ |
| 说明与验证 | 导出、注册、配置、文档、场景和测试是否与真实行为一致？哪些结论还没有证据？ |

专项检查选用当前任务需要的方法：UI 使用 [ui-review](../ui-review/SKILL.md)，同时查控件实现、
MeowUI 归属、主题及浏览器效果；执行链路使用 [runtime-check](../runtime-check/SKILL.md)。
只加载有关方法，不为了“全面”调用所有技能。专项检查已经回答的通用问题直接复用证据，不重复走流程。

例如设置页保存按钮，既检查样式、键盘和窄屏，也追踪保存事件、失败反馈、重复提交及状态归属；
多个页面各自仿造按钮，既是 UI 复用问题，也需判断公共能力是否缺失或调用方是否用错。
页面全部打开过不能代替行为检查，测试全绿也不能代替实际画面判断。

## 核实发现，归并根因，再整改

发现记录对象、触发条件、预期与实际、源码或运行证据、影响及负责位置。主动检查反例和已有保障，
区分真实缺陷、已确认规范的偏离、改进建议和未知；不要为证明巡查有效而强行找问题。

跨块出现同类症状时追共同依赖，能归于同一根因的合并处理，并保留全部受影响入口。
优先修责任归属和既有机制的使用，再考虑增加机制。归属、残留与重复争议按需使用
[defrag](../defrag/SKILL.md)，设计取舍按需使用 [design-steward](../design-steward/SKILL.md)。
若多个块的责任划分、依赖或协作关系需要重新设计，按需使用
[architecture](../architecture/SKILL.md)，带入跨块证据与必须保住的承诺；
它负责整体安排，本技能继续负责覆盖、整改与复验，普通结构梳理无需额外加载。
局部发现不自动推翻整个架构；没有真实需求就不引入新的状态、协议、中间层或全局重构。

按影响和依赖决定顺序：能解除多个局部问题的公共修复优先，独立项继续推进。
修复后重复原触发路径，并核对相关消费者。公共合同、主题或实现变化时，重开受影响的验证，
保留仍有效的无关证据。专项技能负责具体验证标准，根 AGENTS 负责执行环境与权限。
memory 与 non-memory 保持独立变更和验收；整顿不授权删除数据、修改无关服务或发布。

范围外问题记录位置和影响后继续本轮；它确实阻碍本轮完成时说明依赖，不偷偷扩大整改范围。
浏览器、账号或运行环境不可用时留下具体缺口，继续独立部分，不能把无法复验写成通过。

## 用一份轻量记录支持推进和续接

复用已有任务记录；跨批次工作没有记录时，在相关模块文档目录创建一份 Markdown。
记录服务于分治整改，不是新产品状态、永久质量门禁或另一份 roadmap。无需为此开发扫描系统。

保留范围与基线、结构关系及依据、分块对象、问题与证据、整改和复验、当前批次与下一步。
例如使用“块/对象、通用与专项检查、发现/公共根因、处置与证据、进度”几列即可。
无问题项也留覆盖说明；重复根因引用同一记录，不让受影响对象从清单中消失。
证据绑定具体入口和适用分支：注明检查了哪个用法、哪些状态及在哪个版本运行；不能用一个“组件通过”
覆盖整组不同消费者。场景或测试与实际入口配置不同的，单列证据缺口，不据此推断产品已经失败或通过。

读过、检查过、修复落盘和复验通过是不同进度。只巡查时完成指适用检查及发现报告完成；
整改时还需修复复验或用户明确接受保留。不能中途改变口径来关闭问题。
每批完成后更新并继续，不停在计划或进度汇报。中断前保存当前对象、变更、待验项、阻塞及续接入口；
恢复时比较基线和工作区变化，只重开受影响结论。旧截图和测试不能替新版本背书。

## 回到整体收尾

重新对照结构、入口和实现检查遗漏、新增及移动的对象；再走公共层到消费者的关键路径，
核对各块的假设、状态交接和组合行为。局部全部完成不自动证明整体成立。
发现的共同模式可以修正已有组件、规范或文档，但须有本轮证据，不把一次观察升级为永久机制。

声明范围内每个对象都应有处置和适用证据，不要求枚举无限数据组合；必查维度缺失仍是未完成。
最终说明结构判断、主要通用与专项问题、公共根因及整改、验证环境与结果、剩余缺口和记录位置。
若报告数量，明确对象粒度及新增/排除变化；不按改动文件数、派发数或问题数计算完成度。
受阻或仅部分完成时如实交付可续接的进度，不以缩减范围宣称全量通过。
