# 变更与评审约定

本文是本仓库的开发维护约定，由根 AGENTS.md 按任务路由。涉及模块职责、公共合同、
状态所有权、生命周期、权限或持久化的实现与评审，先读相关条目，再核对模块自己的现行合同。
这些判断不证明实现或运行行为已经成立，也不要求局部低风险改动另建流程或设计文档。

## 判断与方案选择

- 架构层面的判断必须先复核再改动：涉及模块职责、公共契约、状态所有权、生命周期、权限或
  持久化时，先沿实际调用链核对相关消费者、现有实现与测试，说明具体触发条件和受损行为。
  Review 发现是待核实的判断，不因自己或子 Agent 已给出结论就直接实施；反证成立时撤回或
  缩小问题，不为保住原建议继续补机制。运行判断核对原输入、执行身份和冻结范围，不用
  后续反馈或别轮现场替代原证据；测试通过和多位 reviewer 同意都不证明新增机制有必要。
- 遇到问题先检查责任边界和已有机制是否用对，再考虑增加机制。正常工作结果不能因处理不便
  被升级成系统故障；也不能靠放宽权限或忽略错误掩盖问题。
- 新增计数、状态、重试分支、协议或中间层前，说明现有机制为什么不能解决；“可以处理眼前案例”
  本身不足以证明有必要。优先修正错误的抽象，并检查同类入口，而不是逐个堆补丁。
- 架构修复方案要比较复用现有机制、修正宿主接线与改变公共契约的实际代价，选择能完整解决
  问题的最小改动。确认其他消费者依赖的合法行为仍成立；不能把负担移给调用方、静默收紧
  产品能力或改变完成标准来让方案成立。代码行数少不等于改动小，也不为旧实现自动增加兼容开关。
- 实施前按受影响的合同推演正常路径和关键失败窗口，例如并发输入、取消与关闭、提交后回执
  丢失、重启重放及存量数据接续。确认现有身份、事务、租约和恢复入口确实能支撑方案，不把
  “已有某接口”当作组合语义成立的证据。会改变方案选择的未知先查明，必要时做最小验证；
  不能用新状态、重试或门禁掩盖未知。跨模块修复须验证接合处，不能只靠各模块单测通过。
- 工具参数、业务失败和权限拒绝通常作为调用结果交回 Agent，由它决定修正、换路或结束；
  宿主负责权限、数据一致性及整体预算、超时、取消，不另设局部纠错次数来代替任务判断。
  已有授权范围内的读取，已有准确地址和可用入口就直接调用，不要求 Agent 先证明宿主权限
  或重复发现地址。拟增前置条件时先核对现有入口的实际处理，不能将下游负责的裁决移给模型。
- 验证错误是否到达正确的处理者、状态是否一致、工作能否继续；不擅自规定 Agent 的纠错次数
  或执行路径。说明方案时区分源码事实、设计推演和运行验证，未验证的恢复或性能效果不能写成
  已确认。上述原则用于实现和 review，按改动风险执行，不要求每个小改动额外产出设计文档，
  也不设置固定思考轮数或重复审批；已有授权和证据充分时继续完成工作。
- 警惕保障性过度工程：验证、交接、防错机制的复杂度应与实际风险相称。先问“去掉它，哪个
  具体场景会变坏，已有机制能否发现或恢复？”不要把一次验收需要、推荐步骤或主观质量判断
  固化为永久状态、协议或执行门禁；同时评估减少的错误、误阻断及新增的维护与恢复成本。
  先区分当前合法路径被误阻断、当前合同有争议和尚未支持的新需求；按读取、幂等写入、非幂等
  写入及不可逆操作分别判断，不对整个机制一刀切。
  保留权限、数据一致性和资源边界等必要保护，不靠减少验证或改写完成标准掩盖未完成工作。

## 模块接入

模块接入以明确的职责、公共输入输出和唯一状态所有者为依据。设计未完成且已混入产品的功能，
先退出默认入口与发行组装，保留研究材料及已有数据；设计已确定而实现不完整的，补齐实现和
验证，不以“实验功能”长期绕过合同。尚未接入的候选不创建空模块，也不为清理删除恢复入口。
每个模块通过公共接口注入宿主依赖，能独立验证正常、失败及适用的恢复路径；产品另验组合处。
独立闭环不要求每个模块另建进程或数据库。当前梳理见[模块生态审查](../architecture/repo/module-ecosystem-review.md)。
