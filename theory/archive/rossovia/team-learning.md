# 团队的工作方法与学习

状态：团队自己写、持续修订的工作文档。内容维护 owner 是协调者；团队所有成员都可贡献经验和改法，书记员协助整理来源与导航。本文保存我们从实际工作中得到的可用方法和已核实项目偏好，与[协作分工和接续规范](collaboration.md)分别维护。

## 怎样继续写这份文档

遇到重复误解、返工、错误假设或有效的新方法，我们写清事实、原因和准备沿用的改法。协调者主动维护、合并与修订内容，必要争议由协调者裁决；多人贡献时先分配文件编辑 owner，避免同时覆盖。日常修正直接进行，不为每条经验增加审批或固定复盘仪式；涉及设计机制时仍沿[独立质疑与共识](design-challenge.md)。

方法保留适用范围和转向条件。后续相关任务观察它减少哪种返工、是否增加不必要成本；有反证就改，失效就撤，重复就合并。用户纠正是重要来源，但每句话仍须按当时语境理解，不扩成全局硬规则，也不以规则数量衡量学习。

专项方法继续引用原清理、测试、文档或设计 owner，不在这里复制正文；必要现场因果证据留原 records，剩余项留原计划。本文不逐条堆历史，不用“记住教训”代替修复未完成的产品缺口。

一条方法只有能改变下一次行动才值得留下：指出容易犯错的原因、具体改法和适用边界。派了谁、读了什么、完成哪一步都留现场记录；只复述共同规则、无法区分行动的口号不作为学习成果。

## 目前值得沿用的方法

### 从工作方式的变化识别需求

熟悉的分类容易遮住用途：把团队学习归入协作规范，会只写分工；把自动化判断理解成手工决策，会交付一个仍需人串联的工具。关键词相同，所需结果却不同。

准备方案前，用一句话说明谁原本在做什么、希望哪一步由系统接手、什么结果表示改变已经发生。再据此选择职责和入口。例如流程自动化必须说明判断由什么触发、谁消费判断、如何取得动作回执；只接通模型调用还没有接通流程。交付为 App 只说明入口形态，估算前仍须核对用户要用它完成的工作，不能把能安装、能聊天代替编程协作。适用于新用途或反复被纠正的需求，明确的小修不反复重问。

### 冻结语义，不能只冻结名字

同名输出可以来自不同分支，携带不同 schema；只保存输出名和定义修订，恢复时仍可能选错校验合同。外部 action ID 与 owner 的 change ID 也不能因为代表同一业务动作就互换。问题出在身份的粒度不足，而非缺少更多重试。

跨中断、恢复或重放时，先问原 owner 用什么准确区分这一次工作及其合同，再从原记录取得身份。冻结会影响后续行为的选择，不在恢复时按名称、最新配置或重新判断猜测；已有记录能承接就不加第二套账本。适用于异步交接和持久工作，纯即时局部计算无需附加这些状态。依据见[输出合同与恢复证据](../records/2026-10-11-workplace-integration.md)。

### 用可验收的交付判断距离

Agent 开发的推进受未决问题、任务依赖和反馈速度影响，不能把传统人日乘除套成工期，也不能把工作包或预设轮次数量当作完成比例。

规划从真实用户场景拆出可观察的里程碑，说明已有证据、下一项会解锁什么、哪些贡献可并行，以及哪个未知会改变路径。新证据到来后更新判断，不另造“agent 日”替代人日。这用于判断剩余交付距离，实际运行耗时仍按真实观察记录。

### 先辨认处理单位，再定义完成条件

连续消息可能是补充、纠正或撤回，不能因每条消息有身份，就把它们视为各自需要答复的工单。给一条回复附上所有输入 ID，也不能证明内容正确；这种校验会让“用 A，改用 B”的正常处理被误判为遗漏。

先用真实例子确认消费者处理的是单独请求还是完整批次。对积累后统一处理的消息，保证接纳、完整交付和上下文关系，按原 Call 与实际产物回执核对执行；内容是否理解正确另做行为验收。只有产品明确承诺逐项交付时，才建立逐项义务。新增状态前，用这个例子做消融，检查它是在保障合同，还是擅自改变工作模型。

### 让证据的范围约束完成声明

测试通过本身没有说明消费者、版本和运行路径：旧快照的通过不能证明后来修改的接合，某个子测试成功也不能把整个失败命令改称通过。反过来，未受影响的有效证据无需因为版本号变化而全部重做。

验收时把要声明的行为对应到代码版本、实际入口和观察结果；只为变化的合同或具体未决风险补证据。复现失败先核夹具是否沿用生产身份与入口，再决定修夹具还是生产。这样既避免用绿色掩盖缺口，也避免反复检查拖住交付。具体方法沿[测试价值](testing.md#测试价值)，现场材料留[整合记录](../records/2026-10-11-workplace-integration.md)。

### 从接收效果选择接线，而非从可用 API 出发

“提醒当前协调者”“唤醒闲置回合”“给指定 agent 派活”需要不同的接收效果。先想到 App Server 消息能力，容易给只需补充当前上下文的需求增建消息桥；已有 Hook 返回协议就能承接这类提醒。

先确定接收者在哪里、现在是否运行、需要上下文还是实际执行，再找宿主已有入口。把判断结果投影成提醒时保留来源和原身份：提醒不是动作回执，历史提案不是新待办，效果未知时先核原动作，不能据提醒重复分派。适用于事件与团队工具接线；跨接收者或真正需要唤醒时，再使用对应平台能力。当前接口见[团队工作流工具](../../scripts/team-workflow/README.md)。

### 用原话校准会改变实现的约束

摘要容易把边界放大：“WorkCell 不理解模型品牌和评分”被转述为“不做任何排序”，会误删资源准入；“未知不能自动重跑副作用”被转述为“不能再 POST”，会阻断原身份的幂等接纳。多人沿同一摘要工作，也不能让它成为用户原要求。

跨角色交接中，凡是会触发删除、拒绝或新增状态的约束，附上最小必要原文，并区分用户决定、当前源码事实和设计者解释。收到具体反例时回核原文与原 owner 的保证，撤回过强解释；不要靠新增标志或第二套事实保存错误前提。只对能改变方案的接缝这样核对，不要求逐项重复用户全文。
