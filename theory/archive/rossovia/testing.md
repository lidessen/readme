# 测试原则与执行规则

新增、修改、评审或清理测试时读「测试价值」与取舍示例；执行检查时按技术栈读取
「执行与证据」中的相关条目。场景选择见[测试入口](../testing/README.md)，多轮进度由
[test-cycle](../../.agents/skills/test-cycle/SKILL.md)组织，不要求每次任务加载全部测试资料。

## 测试价值

- 测试围绕真实行为、公共合同和具体风险编写。写之前能说明：什么输入或操作会触发、错了会损害什么、哪个断言能发现。说不出具体错误的测试不写；不以用例数量、覆盖率或“每个函数都要测”作为目标，也不为每次改动机械补测试。
- 断言检查消费者可观察的结果、副作用和必要不变量；预期来自需求、协议或独立样例，不复制被测算法来计算。不锁定无合同意义的私有结构、调用顺序、调用次数或整份快照。短小的边界测试可以有价值；简单透传、赋值、常量以及类型系统或现有检查已完整保障的事实，不另写同义测试。
- 不通过读取源码、匹配字符串来代替行为测试。确属静态架构约束时优先用类型、lint 或依赖检查；确需专门测试的，必须能发现具体违规。文件、manifest、生成代码和发行产物本身属于合同的，检查其有效内容或实际消费结果，不只检查文件存在或出现了某个词。
- mock/fake 用于隔离测试范围外的依赖或控制具体失败窗口，不能替换本次要验证的机制。测试须经过真实被测入口，独立断言结果；只验证 mock 返回了预设值、被调用过或自建假实现正确，不算产品验证。涉及宿主接线、权限、持久化、恢复或生命周期的，验证对应真实边界；各端单测通过不代替接合处验证。
- 选择能发现目标错误的最小测试范围，优先扩展已有用例。不同层测试各自负责不同风险，不把同一事实逐层重复；参数化覆盖有区别的行为分支，不穷举同义输入或假想组合。测试成本包含夹具、运行时间、误报和维护负担，不为低风险行为搭大型环境或新增测试专用框架、生产开关与公开接口。
- 修复缺陷时，回归用例应复现原触发并在缺陷存在时失败；恢复旧逻辑后仍通过的断言需要重审。用实际触发输入和关键副作用区分正确与错误，避免只断言“不报错”“非空”或 HTTP 200。性能、并发、取消与恢复结论分别需要对应测量或失败窗口，不能靠测试名和一次正常路径宣称覆盖。
- 修改相关实现或测试时同步审视已有用例：无独立保护价值的删除，重复的合并，锁死实现细节的改成行为断言，失效的按现行合同重写。清理限于本次范围；不能只删掉报错断言、放宽必要期望或跳过测试制造绿色。必要风险已经覆盖后停止补测，不给测试再套一层无价值的测试或永久门禁。

## 测试取舍示例

选择用例时先确定要发现的错误，再选择能观察它的入口与断言。下面是取舍示例，不是现有
测试逐项审计的结论，也不要求把每条示例各写成一个测试。

| 常见低价值写法                                              | 更有价值的验证                                                                                                       |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| 读取源码，断言含有某个函数名、调用片段或错误文案            | 经真实入口触发对应行为，核对结果和副作用；静态禁用依赖或 API 优先由依赖检查、类型或 lint 承担                        |
| 给 mock 设定成功返回，再断言 mock 被调用或返回值相等        | 使用真实被测逻辑，在外部依赖边界模拟成功或失败，核对产品输出、错误去向与状态；调用次数只在重复提交等合同相关场景断言 |
| 原样复制算法算出期望，或将本次输出直接存成 golden           | 用独立的输入与预期验证规则；golden/snapshot 只保留有合同意义且可审阅的稳定部分，不自动接受更新                       |
| 只检查文件存在、manifest 出现某个词、生成源码含有某个调用   | 解析并核对有效合同，必要时让真实消费者加载或执行产物；发行检查核对包内必需资源及实际启动                             |
| 多层测试重复同一赋值、透传或默认常量，枚举大量等价输入      | 在合适层保留有独立价值的用例；新增输入要揭示不同规则、边界或失败，跨层用例负责真实接合风险                           |
| 名为权限、恢复或取消测试，却只断言“不报错”、非空或 HTTP 200 | 触发拒绝、重开、重放或在途取消，核对数据、副作用和资源边界；例如被拒写入不能留下数据，重放不能重复产生副作用         |

源码结构检查、mock、短测试和快照并不因形式本身失去价值，关键是它们能否发现所声明的错误。
例如解析器的一个非法输入，可能直接保护权限边界；普通赋值的十组样例则可能没有新增保障。
纯文案、样式或低风险可逆修改可用现有静态检查和实际查看验证，不机械新增单测；交互行为变化
仍需验证实际操作。权限、数据一致性、幂等与恢复所需的测试不能以“减少测试”为由省略。

清理已有测试时沿本次改动范围判断，删除无独立保护价值的用例，合并重复用例，替换脆弱断言。
仍有价值但夹具过重的测试先缩小隔离范围；已发现的产品缺陷不能靠删除失败用例消失。

## 文件组织

测试文件按所属模块与执行方式组织。目录用于帮助找到负责的合同，不以文件数量、
实现文件数量或历史改版批次拆分测试。

- Bun / TypeScript 包的测试集中在包内 `tests/`，`src/` 保留生产实现。`tests/unit/`
  放 `*.test.ts` / `*.test.tsx`，覆盖无需真实浏览器的行为、渲染输出与模块接合；
  `tests/types/` 放 `*.types.ts` / `*.types.tsx`，用类型检查验证公共 API 的合法用法与
  `@ts-expect-error` 非法用法，避免被 Bun 当作运行时用例收集；`tests/browser/` 放
  Playwright 的 `*.spec.ts`，验证真实 DOM、键盘、表单、布局与生命周期。
- 各执行目录下按当前职责分组，例如 MeowUI 的 `components/`、`chat/`、`icons/`、
  `style-system/`、`theme/`。文件以组件或合同命名；组件的结构与属性测试归组件，
  主题生成与配置测试归主题，不按曾经的改版或迁移命名。存在多个独立风险时可以分文件，
  不要求一个实现对应一个测试，也不把所有组件合同塞进一个大文件。
- 测试使用真实被测入口。公共用法优先从包的导出入口导入，内部算法可以直接导入
  `src/` 中的负责模块，不为迁移测试新增生产导出。仅在确有多个消费者时提取
  `tests/helpers/` 或 `tests/fixtures/`；不为目录整齐新增测试框架。
- 单测负责规则、输出和状态合同，浏览器测试负责真实浏览器接合。两层分别发现什么错误
  要清楚；浏览器用例不逐条复制单测中的常量或渲染结构断言。样式生成结果可以作为合同
  验证，但配色与尺寸选择本身不靠固定常量断言验收。测试夹具主动定义的配置值、调用方
  提供的尺寸和触摸目标等必要边界可以使用明确的独立期望，不能与锁定默认外观混为一谈。
- Go 测试继续与实现同包，使用 `*_test.go`；Deno 测试继续使用 `*_test.ts`，遵循
  对应运行模块的目录和配置。应用组装、发行与消费者接合测试由应用维护，不移入被消费的库。
- 新建 Bun 包采用上述布局。存量包在修改相关测试范围时集中整理，避免仅为规范启动全仓迁移。
  本次 MeowUI 完整采用该布局；其他包尚未迁移的路径以各包现行入口为准。
- 迁移时同步更新 import、测试命令、CI、类型检查 include 和现行文档；历史记录保留当时路径。
  不保留新旧两套测试或旧目录转发文件。运行时测试通过与类型用例通过分别验证。

## 执行与证据

- 根目录是 Bun workspace。`bun run dev:dashboard` 启动 Dashboard，`bun run dev:ui` 与 `bun run dev:workshop` 进入产品场景 Workshop。已安装的 `meowbook` 是开发依赖；通用 JSX/CSS/Tail/Book/Press 的实现与库测试归独立 [Meowland](https://github.com/lidessen/meowland)，本仓库不重跑旧库源码测试。旧通用 `apps/storybook` 与重复库已退出；Notes/Tasks 数据和历史不因此迁移或删除。
- 修改前端、共享 JSX / UI / 主题或 meowpress：至少 `bun run check`；它不代替 Go、Runner 或浏览器验证。
- Bun 单测在根目录显式指定目录运行：`bun test apps/meowland/assistant/tools packages/workcell-runner apps/meowland/web/src`
  （根 `bunfig.toml` 排除 `*.spec.ts` 和 `*_test.ts`；Playwright 用 Bun 执行已安装的 CLI：`bun node_modules/.bin/playwright test`，Deno 测试用 `bun run test:deno`。各实际消费者声明公开 npm 依赖，不使用旧 workspace 链接或源码 alias；不通过临时下载替换锁定工具）。
  裸 `bun test` 还会收集安装脚本测试，在无 `curl` 的 Docker 镜像里失败，属环境问题。
- `meowjsx` core 的独立类型检查不加载 DOM/Bun 类型；Web 包单独检查浏览器类型。
  修改两者还需运行包内测试；terminal 占位测试不代表 TUI 行为验收。
- Go 命令进入对应 module：根 module 在仓库根直接运行，覆盖 `internal/**` 与 `apps/**`（例如
  `go test ./internal/toolkit/...`、`go test ./apps/meowland/assistant/...`）；`apps/meowland` 没有自己的
  `go.mod`，在该目录执行 `go test ./assistant/...` 由 Go 沿父目录解析到根 module，所以两种写法都成立。
  独立 module `internal/cellhost/examples/platform` 与 `scripts/go-tools` 则要进入各自带 `go.mod` 的目录执行，
  根 `go list ./...` 不含它们。按风险运行 test / race / vet / build。
- `apps/meowland` 的 Go 测试用 `scripts/go-test.sh`：`fast`（`-short`，包并行；加 `--changed` 只跑 `git diff`
  改动的包及其依赖方）日常迭代用；`full`（重型包 `-p 1`，其余并行）收尾前用；`pkgs <包…>` 跑指定包。
  迭代中不必每次跑 `full`：改哪个包就 `pkgs` 或 `fast --changed`，`full` 只在提交前跑一次；只改文档、golden
  或其他语言测试而没有生产 Go 代码变化时，沿用上一次绿色的 `full` 结果。
  `-short` 会跳过启动真实 Deno / CellHost / Git / 进程的测试（`internal/test_env` 的 `SkipShort`、
  `LookPathDeno`），所以 `fast` 通过不代替 `full`。新增此类测试须在开头调用 `testenv.SkipShort(t)`
  或 `testenv.LookPathDeno(t)`；写可执行夹具用 `testenv.WriteExecutable`（macOS 对每个新 inode 首次 exec
  扫描约 0.5–1 秒，缓存为内容寻址的共享 inode）。无共享可变全局和 `t.Setenv`/`t.Chdir` 的测试加 `t.Parallel()`；
  会 Close 后重开同一托管根目录的测试保持串行（见 `managedfs` registry flock）。
- Pi/CLI Runner 都位于统一包 `packages/workcell-runner/` 的 `src/integrations/<product>/<implementation>/`；共用 contract、host 和 transport 位于 `src/runner/` 与 `src/transports/`。修改时还需 Runner test 和 typecheck。
- `packages/workcell-pty-transport/` 是独立 Bun transport lib；修改时运行其 `bun test`、`bun run typecheck` 和格式检查。它不等同于 TUI renderer，也不替代结构化 Runner integration。
- 视觉或交互改动必须实际打开页面。运行链路的具体检查见 [runtime-check](../../.agents/skills/runtime-check/SKILL.md)。
- 通用 UI 组件先在独立 Meowland 的 `packages/meowtail` 实现，补齐 Meowbook 场景并实际查看、发版后再接入业务页面。不要在产品仓库复制通用实现；业务状态与生命周期仍由应用负责。
- 协议、持久化、幂等、恢复、权限和事件顺序用确定性自动化测试。
- Agent 行为用现场手册，由人或独立代理操作真实产品；不写测试专用 loop、固定阅读批次、
  工具顺序或最低步数。预算只是安全边界，不能变成流程。具体见 [agent-eval](../../.agents/skills/agent-eval/SKILL.md)。
- 区分格式通过、测试通过、行为观察到和用户验收；未验证或受阻之处明确说出。
