# 项目协作与工作接续

状态：当前协作与接续规范；2026-10-11，协调者与独立设计质疑者已就提取范围和分工规则明确一致。本文持有职责分工、任务交接、证据验收和中断续接方法；团队自写的经验、方法修订与核实项目偏好归[团队学习文档](team-learning.md)，文档归属由[文档管理](documentation.md)持有，机制共识由[设计质疑](design-challenge.md)持有。

本方法适用于人类与不同工具中的协作，职责可由人或 agent 承担；项目执行中的主 agent 对应协调者，受委派的子 agent 对应承担有界职责的独立参与者。不指定平台、模型、委派 API 或并发数量。当前环境的授权和部署约束仍须遵守；执行环境按[执行与证据](testing.md#执行与证据)核对，不从协作角色取得额外权限。

## 职责按任务分配

| 职责         | 持有什么                                                 | 如何交接                                                          |
| ------------ | -------------------------------------------------------- | ----------------------------------------------------------------- |
| 协调者       | 战略方向、重大取舍、分工与资源、工作流机制和最终交付判断 | 按用户结果据角色回执决策，维护团队方法，不代具体方案或执行        |
| 规划者       | 当阶段主要／次要矛盾、转化条件及范围、依赖和顺序建议     | 给出优先级、延期与可改变判断的验证，交协调者裁决                  |
| 实现者       | 有界任务的源码读取、实现、测试、日志分析或核查           | 完成最小完整改动，返回结论、文件定位、验证和风险                  |
| 设计监督     | 长任务中对已采纳设计的理解与落实检查                     | 持续发现职责偏移和机制膨胀，追到修正或反证                        |
| 推进者       | 已确定顺序与范围的落实、有限剩余和交付条件               | 收敛讨论与检查，报告阻塞、膨胀及成本，不自行换目标或降合同        |
| 设计质疑者   | 机制方案的独立质疑与共识                                 | 按[设计质疑规则](design-challenge.md)介入，与作者、实现者保持独立 |
| 书记员       | 合同状态、已采纳决定与证据的归位                         | 按[文档规则](documentation.md)介入，不代产品裁决或技术验收        |
| 项目整理者   | 当前触碰范围的消费者、归属与旧路径清理                   | 按[维护入口](README.md)选方法，避免为整齐扩大范围                 |
| 验收与测试者 | 独立核对用户结果、真实入口与受影响合同                   | 返回通过、缺陷、未覆盖及复现，修复交原实现者                      |

这些是职责，不要求每个任务配置固定数量的人员或执行单元。[角色定位与独立指令](team-roles.md)持有注意、判断和纠偏偏好，不改变这里的分工规则。长复杂任务明确委出规划、方案设计、设计监督与推进贡献；简单任务可由同一参与者合并有界贡献，已触发的评审／质疑／验收独立性不能省。普通实现细节由实现者决定，关键歧义交协调者处理。

Workplace 当前 Goal 的具体固定负责人、灵活贡献及接续安排见[原实施计划](../plans/workplace-implementation-plan.md#goal-与本轮团队配置)，不在本规范复制人员配置或进度。

协调者不默认兼任具体方案作者、设计监督或推进者。设计负责人是明确方案作者的任务责任，可由具备该能力的实现者或专项设计参与者承担，由其与独立质疑者达成机制共识；协调者处理战略与重大取舍，不代写方案。这不是第十项常驻角色。设计监督核对已采纳合同与落实证据，不以作者自审代替已触发的独立审查。

规划贡献在切片结论、新阻塞／反证或目标变化时介入，给出当前主要／次要矛盾及转化条件、范围依赖、顺序与延期建议；协调者裁决，推进者按确定安排落实并提供阻塞与成本证据。规划只更新原计划，不每次工具调用重规划，也不新增评分、账本、会议或调度层。

协调者裁决阶段方向、资源冲突与跨职责重大取舍；已确定目标和范围内的局部安排由对应 owner 自主处理，不逐项请示。

协调者同时承担用户代理视角，核实项目偏好，在重大目标或默认行为可能偏离用户意图时及时纠正；主动维护[团队学习文档](team-learning.md)，接收团队贡献。它不增加角色、常驻执行者或逐项审批，书记员只协助来源与导航整理。

源码读取、实现、测试和日志分析交给实现者；已触发的具体代码评审委派给未参与该改动的审查者，不能由作者自审替代，不要求每个小工作新增评审角色。协调者依据回执和关键 diff／证据片段验收，不重复接管子任务；有疑问时定向追加核对。协调工作可以直接完成。

实施者仍负责必要单测和受影响检查；独立验收者不参与受验改动的实现，提供用户结果与实际边界证据，协调者最终据证决定交付。验收不成为实施者转移检查责任的理由，也不为每个小改动新增门禁；需要修复交原 writer，文件所有权先协调。

跨模块迁移、退出旧模型或大量归位时，协调者指定独立项目整理者核对本次受影响范围；日常局部清理仍是实现者义务，不为每个 patch 加人、全仓扫描或增设门禁。具体源码清理遵守委派与文件所有权，不挪动或删除历史证据。

## 划分任务与文件所有权

只有具体、有界且能够独立推进的贡献才并行，按实际资源安排，不为凑数量拆任务。耦合判断、顺序依赖和小工作保持在一起；多个文件、人员或话题本身不是并行理由。

开发期间即可独立测试已完成、未受影响模块或约定稳定接口；交接明确代码版本或快照、场景目标和环境，不把施工中已知中间态当缺陷。无需等全开发结束，界面／API 接合稳定后递进验新；只有新修改、真实失败或具体风险才复测，不重复已绿检查。

每个跨模块切片由协调者指定联动验收 owner，通常由独立验收者承担；新版稳定后取得该版本的集成证据，再据证交付。旧冻结快照的通过只证明原版本，不能代证后续改动。

交接时给出目标、路径、约束、文件所有权和验收标准，只传最小必要上下文。同一文件同一时段只有一个编辑 owner，必要移交先协调。任务开始和结束核对工作树状态与受影响 diff，保留其他人的改动，不用无关重构扩大范围。

实现者按需读取合同、模块入口与方法，限定搜索范围和输出量；独立读取可批量完成。长日志留项目临时文件，回执只带定位和影响判断，避免全面扫描、重复读取和传回整段日志。

当前环境无法委派、等待或满足必要的角色独立性时，说明具体限制及受影响工作，不暗中由协调者代接或由作者自审。可以继续独立且无争议的工作；忙碌时等待已有贡献完成，不靠重复执行填满时间。

## 进度、证据与收口

在原计划维护有限剩余项和交付条件，避免每个实现者复制一套进度。发现偏离及时在已授权范围修正或交协调者裁决；对已采纳且无新反证的问题不反复打断。低优先级或可延期工作明确归位，不让任务变成无限整改。

- 每个切片明确当前要交付的结果、有限剩余和下一步，持续对照用户目标推动必要路径。
- 发现反复讨论已采纳且无新反证的问题、局部打磨、重复检查或范围膨胀时，主动停止无助当前交付的工作，把非必要后续归入延期并继续必要路径。
- 有争议时聚焦真实失败案例、受影响合同和最小修法，明确具体未决点尽快裁决；已授权且无争议的工作不空等用户。
- 必要合同已承接且有效检查已成立，就据证验收并进入下一项，不无限评审。不得降低合同、隐瞒未验证范围或跳过取消、权限及一致性的必要保障来提速；推进不抢实现者文件所有权，不压掉独立质疑，也不硬设时间或次数指标。

实现回执说明改了什么、为什么、有效检查和未验证范围。协调者区分静态推演、格式或类型通过、行为测试通过、真实观察及用户验收，以受影响合同的证据判断完成；不以提交数量或测试绿色代替目标。检查选择与追加条件按[测试价值](testing.md#测试价值)，只有新改动、失败或具体未决风险才追加验证。

独立验收发现缺陷时，给出复现、受损合同与代码版本证据；协调者裁决后交实现者修复，再由独立验收者按受影响边界复测，书记员回填原计划与记录。沿用原任务承接闭环，不新建问题总账；已知延期项如实保留，不写成已修复。

## 中断与接续

在项目内保留简短续接记录：目标、决策理由、已有产物、有效验证和待办。它用于恢复上下文，不成为第二套进度或合同权威；归属与历史证据按[文档规则](documentation.md)处理。

中断、上下文丢失或没有回执时，先读记录并核对已有工作树和日志，不把无回执当成无产物。能复用的检查不重复运行，必要重跑说明具体原因。保持原任务和沟通入口，完成后在原处收尾；除非用户／任务发起者要求，不自动换入口或归档。
