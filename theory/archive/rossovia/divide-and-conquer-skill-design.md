## 问题与边界

用户希望用现有 sub-agent / swarm 工具处理大体量任务，尤其是在核心设计已明确后，逐个
核对实现，同时保留对跨模块调用、共享状态和整体目标的判断。失败方式包括盲目均分目录、
子报告自洽而系统不通、全量检查被抽样替代、共享写入冲突，以及主 Agent 被报告淹没。

方法采用“全局目标与覆盖 → 有界贡献及依赖 → 真实工具派发 → 证据反馈调整 → 组合验证”。
这些关系可以迭代，不要求固定阶段、人数或角色。分治不必并行，并行不必使用多个 Agent；
swarm 也不意味着没有资源边界和最终整合责任。

本仓库没有同职责的 skill。邻近仓库的 work-orchestration 已表达分解与整合，但同时承担
规模评估、风格角色与 review 编排。本次保留可迁移判断，不引入其人格阵容、固定工作流或
外部工具依赖，也不修改相邻仓库。用户已明确请求独立方法，放在本仓库通用 `skills/`。

## 简化后的执行设计

- 主 Agent 维护一份现有工作表，关注目标、覆盖、依赖与接合，不再建立第二套编排系统。
- 分工只传共同核心与必要邻接关系；局部可自行探索，但公共前提变化要及时传播。
- 工具能力以现场为准：派发、消息、状态和等待使用实际能力；共享目录不能假设写入隔离。
- 调度依据完成证据与依赖释放，而非 Agent 数量、忙碌程度或整批同步。
- 主 Agent 查关键证据及接口，保留整体判断，但不重复完成全部子任务。
- 实现审查采用双向覆盖：实现对象都有检查状态，设计责任都有真实调用路径证据。

Skill 主体保持单文件；只有“逐个实现核对”的具体方法放进按需 reference。研究历史不反向
进入普通激活。`design-forge` 判断设计如何收敛，本 skill 负责组织执行；审查中发现实现缺陷
不自动更改核心设计。

## 验证设计

使用隔离的可运行合成代码样例做实际多 Agent 试跑。执行者得到设计、代码、现有局部测试与
只读审查任务，自主分工、调用协作工具、选择验证方式；不提供缺陷答案或规定阅读/工具顺序。
观察局部覆盖、跨层证据、真实派发与整合、读写边界，不能以输出了计划代替实际执行。

该样例只能探查方法是否被执行及局部/整体证据是否接合，不证明大仓库覆盖、长期调度稳定性、
加速比、真实服务验收或复杂写入隔离。没有匹配 baseline，不宣称改善由 skill 单独造成。

本轮实际结果：

- 独立执行者调用实际协作工具，派出两个并行子 Agent，分别检查输入链路及状态约束；它自己
  负责服务接线、组合验证和最终整合。未向执行者透露预埋缺陷或期望分工。
- 所有 9 个输入文件均有覆盖与证据记录；设计和实现前后哈希一致。被执行的 skill 副本与
  交付正文一致。
- 现有 4 项局部测试全部通过；执行者自行编写并运行组合检查，主 Agent 复跑确认其观察。
  组合观察为 3 项通过、3 项失败，失败归并为两个根因：编码丢失图片使准入看错请求；结果
  消费方用当前 generation 替换旧结果身份。报告没有将同一根因的不同表现重复计数。
- 正常文本与取消路径保留通过证据，报告区分“审查完成”和“样例符合设计”；没有把接线
  缺陷变成新设计要求，没有修改被审查实现。
- skill 格式、正文格式、相对链接、AGENTS 路由与 diff 空白检查通过。

证据等级：观察到实际派发、局部贡献和整体核验。该试跑由用户任务明确要求并行，未验证
自动选择该 skill 的准确性；未覆盖共享写入、失联重派、嵌套分治或长期资源调度，也没有
匹配的单 Agent 对照，不能据此声称更快、更省或在大体量任务中稳定有效。
