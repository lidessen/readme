# 实现与归属检查

仅用于明确要求的实现审查或整改，不作为纯视觉走查的默认步骤。
先从实际入口确认控件在哪里、服务什么动作、有哪些状态，再追到组件、事件处理和样式来源。
只扫 JSX 标签会遗漏动态 Surface、原生 HTML、命令式 DOM、弹层和错误路径；只看截图会遗漏数据与生命周期。

## 实现与行为

核对可见文案、可用状态和点击结果是否与实际业务事实一致，事件是否到达正确处理者。
按控件合同检查适用的正常、禁用、只读、加载、空态、错误及完成状态，不要求不存在的状态。
关注异步返回后草稿或新状态被覆盖、重复提交、过期问题仍可回答、失败被显示为成功等真实问题。

核对原生语义、可访问名称、label/description/error 关联、受控/非受控值、表单提交与重置、键盘路径和可见焦点。
弹层检查打开、关闭、Escape、焦点返回及遮挡；这些行为由组件还是应用负责，以实际合同为准。
MeowJSX 不是 React：检查 Signal 更新、实际 runtime 的注册、挂载与卸载清理；不要用 HTML 字符串
插入代替需要事件与生命周期的渲染，也不要给已有控制器再叠一套滚动或状态管理。

## 公共组件归属

先寻找现有 MeowUI 对应能力及其消费者，区分“已有组件没用对”“公共组件缺能力”和“业务专属组合”。
有实际跨应用或多场景复用价值的结构、语义与交互放在独立 Meowland 的 `packages/meowtail`，发版后由产品消费；应用的请求、权限、
任务状态和页面编排仍由应用拥有。不要因看起来相似就合并不同语义，也不要因只出现一次就重写已有 Button。

检查业务目录中复制的基础控件、用私有 CSS 仿造公共控件、绕开导出/registry/part contract 的实现。
原生标签和应用包装本身不是缺陷：依据合同与真实复用关系判断，不以“全部换成组件”作为目标。
需要提取或补齐公共能力时，先实现 MeowUI 组件及主题、补 Meowbook 场景并实际查看，再接入业务。
迁移同时更新实际消费者、导出、类型与场景，不能只搬文件后留下平行实现。
