# Agent 开发：从 TDD 回到验收

> 2026-11-13 关于 TDD、验收、门禁癌变和职责分工的原始想法。它们是方法形成中的材料，不是已验证结论；后续研讨与试点会改变其中的判断。相关技能见 [agile-development](../../skills/agile-development/SKILL.md)。

## AG-2026-11-13-001A — 从 TDD 回到验收

原话：

> 现在有不少误区觉得 TDD 一定是对的，而忽略了我们为什么要 TDD。开发流程也是，流程本质是为了解决什么问题？怎么化繁为简，怎么去伪存真？测试的目的主要是质量保证、功能验收。那为什么 TDD 对 Agent 比较有效呢？因为它在会话早期画好了重点，一定程度上有效避免了 Agent 在执行过程中注意力转移带来的目标偏离。所以我们要守的不是 TDD 这个东西，而是验收、目标保持。

整理：

- TDD 是手段，不是目的。它同时提供早期目标锚定、可执行验收、反证和回归保护，但这些机制可以分开使用。
- 对 Agent 尤其重要的是：在会话早期把“什么算完成”变成可观察的目标，减少长上下文中的注意力漂移和目标偏离。
- 测试的主要目的仍是质量保证和功能验收；TDD 只是让验收更早出现的一种方式。
- 真正要守的是验收标准和目标保持，不是红绿循环的形式。

去向：

- `agile-development` 以“验收先行”而不是“TDD 先行”组织开发轮次。
- 待验证：注意力锚定、反证、回归保护各自贡献多少；哪些任务值得保留严格红绿循环。

## AG-2026-11-13-002A — 设计的癌变与防御性过度工程

原话：

> 设计的癌变：Agent 非常喜欢加门禁、gates，然后为了通过 gates，不断地添补机制。经常出现为了一个安全门，引入一大堆的冗余机制。防御性思维过重。这种思想有点像军事对抗中满脑子只有防守的指挥者，为了添补漏洞把兵员全部分散到了长长的战线上。但是资源是有限的，所以主动出击、掌握主动权，只关心要达成什么战略目标，而不去计较一城一池的得失。Agent 作为规划者、设计者必须具备这样的思想，才能真正让开发敏捷起来，让测试不再成为桎梏，而是成为有用的工具。

整理：

- 门禁会自我繁殖：为了通过一个 gate，Agent 添加新机制；新机制又需要新的 gate。结果是保障性代码和流程比目标本身还重。
- 防御性思维把有限资源分散到每个局部漏洞上，像把兵力铺在漫长战线上；真正重要的是主攻方向、战略目标和主动权。
- 不是不要防御，而是区分必要防御和防御性过度工程：权限、事务、不可逆副作用等边界必须守住；只为缓解焦虑、没有明确失败场景的机制应删掉或降级为反馈。
- 测试应当成为工具：快速、聚焦、能改变下一步行动；不是每加一个担心就加一道关卡。

去向：

- `agile-development` 增加门禁剪枝规则：每道 gate 说明拦什么失败、为什么在这里拦、删掉后谁接回保证。
- 相邻方法：[assurance-review](../../skills/assurance-review/SKILL.md) 专门审查保障性过度工程；[design-forge](../../skills/design-forge/SKILL.md) 处理被补丁带偏的核心设计。
- 待验证：哪些 gate 是便宜且必要的确定性检查，哪些可以改成提示、反馈或直接删除。

## AG-2026-11-13-003A — 真正的并行与三三制

原话：

> 真正的并行思维：敏捷的开发不是开发-测试-开发-测试的线性活动。我觉得可以参考三三制形成 Agent 三人作战小组，协同快速推进。所以一次开发任务，应该是类似一个连队？一个指挥者，多个三人小分队，根据任务规模扩容。

补充：

> 33 制的核心不是人数，而是职责拆分带来的领域专注的效率提升。我说的不是三人组，而是 33 制。

整理：

- 军事三三制常归林彪，1948 年《一点两面与班组的三三制战术》是文本来源，1946 年秀水河子战斗首次使用；权威材料说班分 3–4 组、每组 3–4 人，以班长为中心品字形，目的是减少机枪、炮火和空袭伤亡，后来扩展到排、连、营、团。
- 流行的“固定 3 人组、进攻—掩护—支援、3 组一班、3 班一战斗群、27 人 800 米”是后人概括；固定 3 人和 800 米未见于权威条令，27 人是满编理想值，角色也会轮换。核心经验是指挥权下沉、失联仍能打，以及按能独立行动、独立验收的最小单元划域。
- 核心不是“3”这个数字，而是职责拆分和领域专注：小组自足、职责明确、分散配置、相互支援、跨度控制。3 人编制是当时条件下的具体形式，不是普适常数；有批评指出它并非三三制独有，部分是缺乏轻机枪和通信的产物，后来苏式化又改为按任务划分火力组。
- 可迁移的是关系，不是人数：按“能独立行动、独立验收的最小单元”划域，组间靠任务意图、合同和相互支援耦合；集中意图、分散执行，每层小跨度、按层级扩容。
- 对应到 Agent 开发：先按职责域划分（切片/模块 owner、验收/反证、未知探索、契约裁决、整合、预备队），再按工作图和 ready frontier 决定最小建制；人数是职责域的结果，不是起点。
- 并行单位应是“一个写者、一条接缝、可独立验收的垂直切片”，不是按文件数或前后端层次均分。
- 相互支援对应独立验证、交叉 review、测试设计和整合检查；不是重复 review，也不是每个失败加一道 gate。

去向：

- `agile-development` 的团队部分应以“职责域 + ownership + 合同 + 任务意图 + 按 frontier 扩容”为中心，默认是主 Agent 加工作小组而不是单 Agent，不写成固定 1/2/3/5/9 编制表。
- 待验证：领域专注对 LLM Agent 是否真的比单人端到端更高效；两人组（owner + verifier / scout）是否比三人组更常见地最优；三人组是否只是职责域模型的一个特例；领域边界怎么划才不会变成 silo。
- 试点设计需要区分“领域专注”和“多人并行”两个变量，比较最终验收时间、token、整合返工和逃逸缺陷。

## AG-2026-11-13-004A — 流程的目的与化繁为简

原话：

> 流程本质是为了解决什么问题？怎么化繁为简，怎么去伪存真？

整理：

- 每个流程步骤都应能回答：它防止哪种具体失败？为什么必须在这里拦？删掉后谁接回保证？
- 化繁为简不是删掉必要保障，而是去掉不承载判断、只为“看起来严谨”的步骤。
- 去伪存真：区分“机械检查通过”和“目标行为成立”；区分“有人 review 过”和“有独立证据”。
- 流程应随风险缩放：小任务走快车道，高风险任务才增加独立验证和更重的门禁。

去向：

- `agile-development` 的每个轮次和 gate 都要有目的、进入条件、退出证据；没有选择点的流程不建立。
- 与 [agent-guidance](../../skills/agent-guidance/SKILL.md) 的分工：后者判断载体是否值得存在，前者组织开发推进。

## AG-2026-11-13-005A — 任务规模与编制判断

原话：

> 什么规模的任务，一个人就够了，什么规模的任务需要启用三人组？
>
> 这里暴露出来一个问题啊，就是任务规模根本没有评估标准，没有办法量化，而且我认为在现在这个阶段，Agent 主导的开发，单 Agent 作为默认是脱离实际的，现在的开发任务你去看看，已经不是人类开发的时候，半天写几百行了。

整理：

- “任务规模”不是行数、文件数或工时。Agent 生成代码的成本很低，真正的瓶颈是上下文、注意力、决策一致性和整合。人类时代“半天几百行”的直觉会严重低估 Agent 任务。
- 规模应该看成一个向量，而不是一个标量：节点数 `N`、最大 ready 宽度 `W`、关键路径 `L`、跨节点合同边 `E`、共享写入资源 `X`、上下文 token `T`、风险级别 `R`、未知簇 `U`、整合容量 `I`。
- Agent 主导的开发，默认应是主 Agent 加工作小组，而不是单 Agent 包打天下。单 Agent 只适合工作图只有一个节点且 `R0`、`U=0`、上下文装得下，或节点虽多但 `W=1`、上下文装得下、`R0`、`U=0` 的串行任务。
- 编制是算出来的：`W>=2` 时至少两个 worker，worker 数约为 `min(W, I, 5)`；主 Agent 可以兼任一个 worker；`R1/R2` 加独立验收者；`U>0` 按未知簇加探索者；协调跨度约 3–5 条活跃线。
- 三人组不是起点。它通常是 `W=2` 加一个验收者，或一个切片加验收者和探索者的结果。若只是两个独立切片，应该是两个 owner，不是三个人挤在一个组里。
- 扩容上限是整合容量，不是任务大小。`W` 大而 `I` 小，加 worker 只会制造合并队列。
- 这些阈值是可校准的起点，不是定律。每次任务结束记录估算和实际，用真实任务校准；没有测量，就不要用“任务大”或“三人组”当编制理由。

去向：

- `agile-development` 的团队部分改为默认主 Agent 加工作小组，并加入工作图指标 `N/W/L/E/X/T/R/U/I`、编制规则和校准循环。
- 待验证：这些代理指标能否稳定预测并行净收益；`W`、`T`、`I` 的实际测量误差有多大；默认多 Agent 相比单 Agent 在真实长任务上的验收时间和逃逸缺陷差异。

## AG-2026-11-13-006A — 根据地建设与环境改造

原话：

> 可以先本地试用, 不过在这之前, 还有一个, 根据地建设或者叫环境改造, 我觉得有必要补充一个这样的 skill

整理：

- 根据地不是堡垒。它的作用是让部队能休息、补给、训练、再出击，不是把兵力钉在防线上；环境改造也要服务于主任务的速度和范围，不能变成新的平台瀑布。
- Agent 开发的速度不只取决于模型和提示词，还取决于环境：入口是否清楚、反馈是否快、失败是否可复现、上下文是否可得、并行是否安全、回滚是否可行。
- 环境改造应从真实任务的重复摩擦出发，而不是从最佳实践清单出发。优先修频率高、损失大、影响任务多、可逆且可验证的瓶颈。
- 最小闭环优先：一条命令跑起来、相关测试快而稳、新 Agent 能靠仓库文档找到入口、并行有隔离、主路径可观察；不要先建通用平台。
- 用 before/after 和 fresh context 测试验收；没有改善就回滚或停止。根据地建设本身也要有停止条件。
- 技能正文不引入军事概念；军事研究只作为设计背景，结构用开发语言重写（工作基线、改造点、本地实验区、外部依赖等），只保留必要的来源说明。
- 与 `agile-development` 的关系：后者组织主任务推进，前者为主任务提供可持续的反馈循环和安全边界；环境改造可以复用前者的起胚和打磨循环。

去向：

- 工作基线和环境改造并入 `agile-development`，用 references 分层：`work-baseline.md`、`environment.md`、`friction-audit.md`、`task-sizing.md`；不再单独维护 `environment-readiness`。
- 待验证：哪些环境投资对 Agent 的净收益最高；fresh context 测试能否稳定预测任务摩擦；环境改造的停止条件如何量化。

## AG-2026-11-13-007A — 通用方法与项目本地化

原话：

> 环境改造(建立根据地) 有一个很重要的原则，那就是要结合项目实际情况（可以看看根据地怎么建设的，类比参考），具体问题具体分析。我的想法是，方法论是通用的，但是具体方法是灵活的，可以在认识项目的时候再确定，像内容记录在哪里，怎么执行 33 制，可以在对项目进行分析之后生成一个项目本地的 md 文件，添加到比如 AGENTS.md、CLAUDE.md。

整理：

- 方法本身是通用的；它给的是判断顺序、检查项和验收关系，不给固定文件名、命令、角色表或团队规模。
- 环境改造和工作基线都从项目认识开始：现有载体、真实命令、目录与所有权、Agent 工具、最近任务的重复摩擦。
- 项目分析后生成或更新一个项目本地工作基线载体（单独一个 md，或 `AGENTS.md`/`CLAUDE.md` 中的段落），记录这个项目的具体决定；单独成文时 `AGENTS.md`/`CLAUDE.md` 作为 Agent 入口指向它。
- 载体只写项目特定决定和权威位置，不复制通用方法；优先复用已有载体，避免第二份互相矛盾的权威。
- 分治与并行（包括“33 制”式的职责拆分）怎么落地，按项目工作图和现有工具决定；人数是工作图的结果，不是起点。
- 同一个摩擦在不同项目里的频率、损失、改造成本和可逆性不同，改造点不能照搬。

去向：

- `agile-development` 增加“通用方法，项目本地化”一节；`work-baseline.md` 增加项目分析和项目本地工作基线载体模板；`environment.md`、`task-sizing.md` 增加项目本地化说明。
- 待验证：本地基线载体能否降低 fresh context 恢复时间；会不会变成又一份过期文档；项目分析的成本是否值得。

## AG-2026-11-13-008A — 两层实践：方法中心与本地试验场

原话：

> 我是这么想的, 分为两层, 这个项目作为总的指挥中心, 我本地有几个项目, 正好用于测试, 而且这个项目是一个博客/skill 项目, 是理论中心, 还挺合适. 你可以用 rex/herdr-core, 看到其他正在进行中的任务, 在那边试用这个 skill, 而这个项目的作用就是观察各个项目的实践情况, 积累观察,进行改进. 另外我提醒一下, 你再看眼 skill, 敏捷是主要诉求, 不要自己形成新的规矩流程卡住开发

整理：

- 本仓库是方法层：维护技能、理论和跨项目观察；本地项目是实践层：在真实任务里试用，不用合成案例代替真实摩擦。
- 观察不必统一格式；可以只记：什么任务、什么上下文、方法帮了什么、卡了什么、下次改什么。
- 技能不能变成新的流程负担：顺序和检查项默认是启发式，不是开工门禁；只有安全、验收和不可逆责任保留为硬约束。
- 观察结果回到本仓库，优先改技能中的判断顺序、检查项和默认值，不急着增加新步骤或新文档。

去向：

- 用 rex/herdr-core 观察或发起本地项目任务，优先选低风险、可回滚的切片试用。
- 在 `theory/thoughts/agile-development.md` 或后续观察记录里积累真实任务证据，再决定是否调整阈值。
- 待验证：两层结构能否在不增加项目侧流程的前提下，形成稳定的实践反馈。

## AG-2026-11-13-009A — 本地项目试用：取证批次

试用方式：在一个项目启动只读 reviewer，让它读技能后评审下一件任务——把验收 harness 入库并用同一套引擎重跑发行构建批次；要求给出最小执行计划、技能帮助点、过程负担和一处改法，不修改仓库。

观察：

- 技能有帮助的地方：最短路径直接指向“重跑现有 harness”，避免把它做成重写工具；环境解阻支持把一次性执行器换成入库的权威实现；第一轮走真实入口支持用完整 smoke 作为第一观察；验收先行和“只保留一个权威实现”对应到绑定提交、产物哈希和引擎版本。
- 技能增加负担的地方：完整基线分析对已有 AGENTS.md、plan、workflow、验收日志的项目过重；工作图指标和默认工作小组不适用于共享 live 机器、浏览器 profile、单套凭据这类串行瓶颈；技能的阶段词和项目自己的短循环并存时，容易变成第二套流程；live 批次的一个未知往往按批次周期计，15–30 分钟太紧；项目本地载体有变成第二份计划或日志的倾向。
- 据此改了技能：增加“取证批次”快车道；明确项目已有更短循环时直接沿用，不改流程、不改叫法、不新建载体；补充共享 live 机器/单写资源的串行优先；把未知时间盒改为可按批次周期计；载体只指向已有 plan、workflow、验收日志。

去向：

- 下一轮试用优先选有真实验收命令、能回滚的小任务，观察“取证批次”是否真的减少流程。
- 待验证：项目循环与技能阶段冲突时，哪些判断仍值得保留；取证批次能否在不牺牲证据质量的前提下缩短交付。

## AG-2026-11-13-010A — 取证批次实跑：smoke 与回归

实跑：在固定的项目版本上用已有 harness 先跑 `smoke`，再跑 `regression`（三个场景各 5 次）；证据留在项目的本地证据目录，未改仓库代码。

观察：

- 技能帮助：取证快车道把任务收敛为固定引擎、提交、产物哈希和夹具来源，先冒烟后正式批次，没有展开成塑形或重写 harness；项目已有的通过线和记录方式直接沿用，没有新建载体。
- 结果：smoke 三个场景各 1 次全部业务成立；回归 15 次业务全部成立，固定计划 5/5 恰好一次，错误动作 0、凭据命中 0、未知投递重发 0、无准备失败；与上一次回归相比，各场景业务成立次数持平或更好。
- 一个判断点：合成页首见形态 3/5，低于业务成立 5/5。它属于诊断数字，不是这批回归的通过线；两次未首见都伴随一次未知投递后的重放，业务结果仍成立。若把所有指标都当门禁，会多出一次假失败。
- 据此改了技能：取证快车道补一句“先采用项目或批次约定的通过线和硬规则，首见率、耗时这类诊断数字单独记录，不临时升级为通过线”。

去向：

- 待验证：这条判断能否防止后续批次把诊断指标误当门禁。
- `benchmark` 没有通过线，本次未跑；等需要发布数字时再按同一引擎补，不在取证任务里顺手扩范围。

## AG-2026-11-13-011A — 理论武装与人类决策接口

原话：

> 还有一个, 我们打造的敏捷团队,应该是理论武装的, 具备主观能动性的, 不仅仅是完成任务, 是要理解任务, 理解战略目标, 这样才能充分发挥主观能动性, 才能做出超预期的工作, 才能不止局限于完成任务, 而能把项目越改越好. 当然, 目前人还是不可缺少的决策者, 假定人作为决策者, 要充分考虑和设计好 Agent 和人的交流机制和方式, 现在的问题是上下文太多了, 人是不可能感知和通读完整上下文的, 所以给人暴露到什么程度, 怎么和人交流是方式方法技巧问题, 这个我在全局的 claude.md 之前已经提过一些要求. 我觉得核心关键是, 每次交流应该是局限的两到三个决策点, 然后补充和扩展必要的, 甚至是冗余的上下文, 使人接受需要认真去看的内容长度, 大概局限在比如500 字以下(这可以在实验过程中继续调整)

整理：

- “理论武装”落在开发语言里，是团队共享方法和项目的目标上下文：知道为什么做、服务哪个目标、什么算更好，而不只是拿到步骤。理解目标才能在取舍时做出判断，把项目越改越好。
- 主观能动性有边界：授权内可以选技术默认、简化、修摩擦、提更好的验收；改目标、公开合同、硬边界和不可逆操作仍由人类或明确 owner 决定。发现方向冲突要带证据提出，不沉默执行，也不擅自转向。
- “超预期”不是范围外抛光，而是更少的机制、可复用的改进、更早暴露风险；仍要过验收。
- 人仍是决策者，但不可能通读完整上下文。交流是接口设计：默认每次 2–3 个决策点，每个自足，带必要甚至冗余的上下文、选项、后果和建议；需要认真读的部分约 500 字以内，背景和证据可展开。
- 500 字是实验起点，不是硬指标；观察决策时间、误解、返工和越界情况再调整。
- 与全局 CLAUDE.md 的“与人沟通的方式”一致：结论和决策直接呈现，每条信息自带上下文，不让人翻前文；背景留在文档，对话只放人行动所需的部分。

去向：

- `agile-development` 增加“带目标工作”和“和人交流”两节，新增 `references/human-interface.md`，并在完成条件、反模式里补对应检查。
- 待验证：2–3 个决策点、500 字预算是否足以让人做出高质量决定；目标上下文给到子 Agent 后，是否减少漂移和返工，而不增加上下文负担。

## AG-2026-11-13-012A — 协调端与项目端：窗口协作

观察方式：协调端向多个项目端交代目标和边界，项目端先读方法、核对项目状态，再自行组织工作并回报。沿用项目已有的工作流、验收命令和记录方式，不为协调新建第二套流程。

整理：

- 分工按任务依赖、共享资源与整合容量决定；并行工作需要明确写入边界，避免多人修改同一工作树，并关注合并队列是否成为瓶颈。
- 窗口状态只是瞬时观察，不是计划、工作区或验收结果的第二权威；决策前回到项目已有记录与实际状态核对，也不要覆盖用户未发送的草稿。
- 状态汇报与决策请求分开；需要决定的事项应自带选项及后果，不依赖对方阅读原始窗口。

待验证：项目端自行组织能否减少额外流程，以及有限长度的回报能否支持可靠决策。

## AG-2026-11-13-013A — 决策点必须自足：A/B 标签不能跨接口

观察：协调端把项目端的“选项 A / 选项 B”直接转给用户，用户不知道 A/B 指什么，无法决定。项目端原文有上下文，但转述时丢了工作区状态和两个选项各自的后果。

整理：

- 决策点的标签是局部上下文，不是接口。转述时必须重新展开：要定什么、每个选项做什么、代价和后果、默认动作。
- “2–3 个决策点、500 字”不是压缩掉背景，而是把背景压到足以独立决策。
- 自足性检查：把消息单独拿出来，假设对方没看过项目端原文；如果对方会问“A 是什么”，就不合格。
- 协调端不是传声筒：项目端的决策点要经过一次“冷读重写”，把项目端内部标签翻译成用户能直接选的人话。

去向：

- `human-interface` 增加“自足性检查”和“不要只给 A/B 标签”的反模式；根技能“和人交流”补一句选项要写完整。

## AG-2026-11-13-014A — 本地提交不是人的决策点

观察：项目端问“现在提交还是留在工作区”，协调端把它转给用户；用户指出，这类已授权范围内的本地提交一般不需要人决策。

整理：

- 本地提交是可逆检查点，属于已授权任务的执行，不是产品或方向决策；停下来问会把敏捷开发变成审批流程。
- 需要人的边界是推送/公开、发布、不可逆、跨项目、超出授权，以及项目规范明确要求确认的动作。
- 项目端也不应把“提交或推送”捆成一个问题；本地提交按任务授权做，推送另问。
- 协调端转述时要把这个边界带过去，而不是把项目端的每个操作问题都升级。

## AG-2026-11-13-015A — 窗口通信：持久消息与安全投递

观察：直接向窗口输入长指令可能覆盖未发送草稿；接收端忙碌时，排队消息何时处理也不清楚。终端输出会滚走，没有持久回执就难以对账；仅凭动画符号判断忙闲也不可靠。

整理：消息正文和回执需要可对账，短通知只用于提醒；投递前检查接收端状态与草稿，状态不明或忙碌时等待。窗口状态是观察，不取代任务及结果的权威记录。重试前先核对是否已经送达，避免重复操作。

证据与限制：模拟检查覆盖了空闲、忙碌和草稿等情形；一次真实投递在接收端完成当前工作后收到回执。事件丢失后的恢复和完整回复路径当时仍待验证，不能把一次观察当作通用可靠性保证。
